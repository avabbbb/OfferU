# 01 · 总体设计

> 状态：**当前设计权威** · 取代 GOAL.md、CONTEXT.md、ARCHITECTURE.md、docs/product/current-product.md 等（映射见 [archive](./archive/README.md)）

## 1. 产品定位

**OfferU 是本地优先的求职工作台（Career OS）。它把「一个岗位」变成一个持久、有证据支撑的岗位工作区。**

- **目标用户**：在校生、研究生和社招求职者。他们在意投递质量和效率，愿意为此投入时间，通常已经在用某个通用 AI。用户不需要会编程。
- **要解决的问题**：每次投递都从零开始。JD 在浏览器里，简历在文件里，研究在另一个标签页，进展记在表格里，面试经验散落在各个聊天窗口。通用 AI 为了「优化」简历，还会编造经历。
- **核心承诺**：给 OfferU 一个岗位，它告诉你岗位真正要什么、你能证明什么、下一步准备什么，并且把这些工作保存下来，不会随着聊天窗口关闭而消失。

```text
目标岗位要什么 × 我能证明什么 → 我下一步该准备什么 → 有证据的岗位工作区
```

OfferU 要同时降低两种负担：

1. **配置负担**：不需要装 Python、Node、Git、MCP，也不需要填模型 ID。
2. **决策负担**：不需要知道下一步该点哪个功能、该用哪个 Skill。

## 2. 核心闭环

```text
职业档案 ──→ 保存岗位 ──→ 岗位研究 ──→ 证据缺口 ──→ 定制简历
   ↑                                                    ↓
复盘学习 ←── 针对性面试 ←────────── 投递进展 ←──────────┘
```

每一步的产物都写入同一份 **Career Truth**（本地持久的职业事实与流程状态）。「今天」、投递看板和 Agent 都只是这份事实的不同投影。

## 3. 信息架构

> **PROPOSAL（待产品负责人确认）**：一级导航收敛为 4 个入口。详细交互见 [02 §2](./02-interaction-design.md#2-导航与信息架构)。

| 一级入口 | 回答的问题 | 包含 |
| --- | --- | --- |
| **今天** | 现在最该做什么？ | 最多 3 个下一步、需要你处理的事项、进行中的任务 |
| **岗位** | 我在推进哪些机会？ | 岗位列表 / 看板视图（即原 Pipeline）、单个岗位工作区（研究、证据、材料、面试、时间线） |
| **简历** | 我的简历现在是什么样？ | 基础简历、岗位定制版本、模板与设计（合并原「工作室」） |
| **档案** | OfferU 对我了解多少？ | 已确认的事实、待确认的候选、证据、缺口、偏好 |
| 设置（底部） | 怎么连接、怎么管理数据？ | Agent 连接、模型、邮箱与日历信号源、备份与恢复、隐私 |

Agent、邮件、日历、浏览器采集、记忆都是跨页面的**能力**，不是独立产品。它们产出的结果落到上面这些页面里。

## 4. 两个入口，一份事实

| 入口 | 适合谁 | 路径 |
| --- | --- | --- |
| **App-first（默认）** | 普通用户 | 安装 Desktop → 导入简历建档 → 保存第一个岗位 → 岗位工作区 → 「今天」引导下一步 |
| **Skill-first** | 已经在 Codex、Claude Code、WorkBuddy、OpenCode 等工具里工作的用户 | 启用 OfferU Skill → 「帮我分析这个岗位」→ Agent 创建或找到同一个岗位 → 在 Desktop 打开同一个工作区 |

规则：

- Skill-first 绝不能变成第二套产品。它不能创建只有 Agent 才能看到的岗位、隐藏工作区或平行档案。
- 连接 Agent 很重要，但**不能卡住首次价值**。没连接 Agent 时，也能建档、保存岗位、打开工作区；需要推理的步骤会明确显示「需要连接 Agent」，并给出一个按钮。
- Web Showcase 只使用浏览器内的演示 Agent 和虚构数据；真实数据只走 Desktop。

## 5. 推理主体：优先用户自己的 Agent，但不只靠它

- 优先使用用户已经登录、验证通过的通用 Agent，复用它的账号和模型，不让用户重复填 API Key。
- 没有合适的外部 Agent，或者用户主动选择时，使用 OfferU 内置 Agent。The built-in Agent remains capable of operating OfferU through the same Skill allowlists, fact gates, proposal path and independent approval as an external host. 内置 Agent 只是另一个推理提供方，不是一套权限更弱的写入路径。
- 每个 Agent Run 只有 exactly one 个推理主体。

> **待决问题（Q1）**：新用户第一次打开时，默认是「先用内置 Agent 立刻出结果，再提示可以连接自己的 Agent」，还是「先引导连接自己的 Agent」？在决定之前，按前者实现：首次价值不依赖外部连接。

## 6. 权威模型（四权分立）

| 权威 | 负责 | 不负责 |
| --- | --- | --- |
| **推理权**：当前 Agent | 理解目标、研究、判断、起草、选择能力 | 拥有事实；批准自己的改动 |
| **执行权**：Operation Registry | 校验、权限、副作用分级、提案、幂等、审计 | 职业判断 |
| **事实权**：Career Runtime（Python） | 持久化档案、岗位、投递、简历、面试、事件、记忆 | 推理 |
| **高风险批准权**：用户（或明确的确定性策略） | 确认职业事实、授权不可逆的外部动作 | — |

只有走完下面这条链，状态才算真正改变；Agent 用自然语言说「已完成」不算：

```text
Operation → 校验 → 权限 → 执行 → 持久化事件或状态 → 审计
```

GUI、CLI、Skill、Agent、自动化、插件、浏览器扩展的**所有业务写入**，都必须经过同一个 Operation Registry。

## 7. 系统拓扑与技术边界

```text
            OfferU Desktop（Tauri）· 今天 · 岗位 · 简历 · 档案
                              │
              ┌───────────────┴───────────────┐
         外部本地 Agent（优先）          OfferU 内置 Agent（兜底）
              └───────────────┬───────────────┘
                 OfferU Skill + 可选的第三方职业 Skill
                              │
                     Agent Tool Surface（精简）
                              │
                Operation Registry（FastAPI，:8766）
                              │
          Career Runtime · SQLite · 本地文件（简历、导出物）
                              ↑
            浏览器扩展（WXT）· 邮件 / 日历同步 · 自动化
```

| 层 | 技术 | 职责 |
| --- | --- | --- |
| UI | React 18 + Vite + NextUI + Tailwind，hash 路由 | 交互与本地 UI 状态，不保存第二份业务状态 |
| 业务 | Python / FastAPI | Career Runtime、Operation Registry、自动化、数据 |
| 桌面 | Tauri / Rust | 窗口、进程生命周期、安装与更新、系统集成 |
| Agent | 外部宿主或内置 Python 内核（`backend/app/agent/`） | 可替换的推理与执行引擎 |
| 数据 | SQLite + 文件 | 本地、单人使用；不做 SaaS、账号、多租户或云同步 |

硬约束：不做 Python 到 TypeScript 的重写；不新增第二套 Node 后端；不直接向公网暴露 8766。

## 8. 自动化与自主等级

只有一种自动化模型，不允许出现第二个无限循环的 Agent Loop：

```text
事件 / 日程 / 状态变化 → AutomationRule → CareerTask → Agent / Runtime → Operation
```

- **Runtime 决定何时思考**：保存岗位、每日回顾、面试邀请、简历更新等明确触发点。
- **Career Director（一次有边界的 Agent 判断）决定什么重要**：输出必须带 `why_now`。
- **Registry 与策略决定能执行什么。**

| 等级 | 含义 | 默认交互（见 [02 §4](./02-interaction-design.md#4-打断规则agent-什么时候来找你)） |
| --- | --- | --- |
| L0 观察 | 读取、分析 | 自动 |
| L1 准备 | 研究、起草、生成可逆的工作区内容 | 在任务范围内自动 |
| L2 改变职业状态 | 采用简历改写、确认事实、确认阶段变化 | 按可逆性和已有授权决定：自动或请你审阅 |
| L3 外部或破坏性动作 | 提交申请、发信、联系他人、删除数据 | 必须由你明确授权 |

Agent 推断、外部信号、面试学习只能先成为**候选**，不能静默改变 Career Truth。

## 9. 非目标

- 后台爬取岗位，作为新手默认的岗位来源；
- 静默提交申请，或替用户给招聘方发消息；
- 第二份 Career Truth、只属于 Agent 的数据库写入路径；
- 一次性把所有 Operation 暴露给模型的大工具目录；
- 在本地 Agent 已经能用的情况下，要求用户重复配置模型；
- 把很长的命令或模式菜单作为新手界面；
- 把历史 Eval 数字当作当前能力。

## 10. 核心术语

| 术语 | 含义 |
| --- | --- |
| Career Truth | 结构化、可由用户编辑的职业事实与流程状态，是唯一权威记录 |
| Evidence（证据） | 能支撑简历、匹配或面试的有来源事实 |
| Candidate / Observation（候选） | 可能相关但尚未确认的新信息 |
| Job Workspace（岗位工作区） | 一个机会的持久工作区：快照、研究、证据图、材料、面试、时间线 |
| Role Intelligence | 把目标岗位与同类岗位对比，区分共性要求和独特要求 |
| Evidence Map | 把岗位要求映射到用户证据：强 / 弱 / 缺失 / 未知 / 表达不足 |
| CareerTask | 一个持久、可重试、可取消的后台任务记录 |
| Agent Run | 一次有授权、可审计的 Agent 执行，有确定的终态 |
| Proposal | 等待审阅的受保护改动 |
| Ask | 向用户提出的取舍或补充信息问题；回答 Ask 不等于批准未展示的改动 |
| Next Best Action | 「今天」页面上从当前状态推导出的下一步 |
| False Success | Agent 声称成功，但没有可信证据证明 |

> 实现状态不写在这里。当前进展看 `RELEASE_CHECKLIST.md`、`KNOWN_ISSUES.md` 和 [`docs/evidence/`](./evidence/)。
