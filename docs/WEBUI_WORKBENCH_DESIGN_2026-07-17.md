## 一句话方向

**Codex 的任务工作台外壳 × Notion 的数据工作方式 × OfferU 的求职领域界面。**

Codex 负责求职任务、历史、Agent 协作、运行状态和确认；Notion 负责数据库视图、属性、侧边预览和渐进披露；OfferU 保留投递时间线、岗位研究、简历编辑、日程和面试训练等专业界面。

## 1. 当前问题

当前问题不是缺少一套 CSS 令牌，而是令牌、页面结构和交互模型没有收敛到同一体系。

### 1.1 量化证据

2026-07-17 对 `frontend/src` 的只读扫描结果：

| 信号 | 数量 | 说明 |
|---|---:|---|
| 硬编码背景色 `bg-[#…]` | 108 | 页面仍在自行定义模块色和装饰色 |
| `rounded-none` | 71 | 与全局圆角令牌直接冲突 |
| 自定义 Tailwind 阴影 `shadow-[…]` | 44 | 与“hairline、无硬阴影”目标冲突 |
| `transition-all` | 10 | 难以控制性能、属性范围和减少动态效果 |
| `motion.*` 节点 | 85 | 已有大量动画代码，但缺少统一语法 |
| `whileHover` / `whileTap` | 7 | 交互反馈并未覆盖用户实际操作 |
| `text-5xl/6xl/7xl` | 20 | 工具页仍大量使用营销式标题 |

### 1.2 结构冲突

- `AI 优化`、`日程`、`设置`等页面首屏被 Hero、解释文案和指标卡占用，真实操作被推迟。
- `Sidebar` 平铺九个模块；导航按代码模块组织，而不是按求职流程组织。
- `/agent`、`HarnessAgentDock`、`ProfileAgentDock`、`OptimizeChatPanel` 同时存在，形成多套 Agent 入口和局部会话状态。
- `studio`、`settings`、`interview/ai` 与主界面在色彩、阴影、圆角和密度上像不同产品。
- 现有 `globals.css` 已声明 Notion 式令牌，但页面内联类仍覆盖它们。
- `/resume` 当前在 `page.tsx:219` 附近存在编译错误，导致部分路由无法稳定进行视觉验收；实施前必须先恢复可运行基线，但不应借机重构无关代码。

## 2. 设计原则

### 2.1 任务优先，不做模块宣传页

- 默认首屏必须回答：我正在处理什么、现在是什么状态、下一步做什么。
- 大型品牌叙事只出现在首次引导和真正空状态。
- 页面标题使用紧凑标题栏，不使用占据首屏的大字海报。
- 指标和趋势是二级信息，默认折叠或进入专门视图。

### 2.2 同一外壳，不同专业表面

- 岗位、投递、日程、任务默认使用列表或表格。
- 对象摘要与轻操作进入右侧上下文栏。
- 简历深度编辑、面试房间等复杂工具进入全屏专注模式。
- Agent 对话不是全部业务界面的容器；领域对象仍由自己的编辑器、表格和时间线呈现。

### 2.3 渐进披露

统一路径：

`列表/视图 → 右侧上下文栏 → 复杂编辑全屏`

- 默认只展示完成当前任务必需的信息。
- 高频动作外露；低频动作进入 `…`、`Ctrl+K` 或上下文栏。
- 同一表面最多一个主按钮。
- 对象详情与主 Agent 共用一个右侧上下文栏，通过“详情 / OfferU”切换，同一时间只显示一种模式。

### 2.4 弹性布局与弹性动画分离

- 弹性布局负责不同宽度下的重排、折叠和单列化。
- 弹性动画负责交互反馈和状态连续性。
- 两者不能用固定像素缩放或整页 transform 互相代替。

## 3. 信息架构

### 3.1 一级导航

| 一级入口 | 用户问题 | 现有路由归属 |
|---|---|---|
| 今日 | 我现在最该处理什么？ | `/` |
| 机会 | 哪些公司和岗位值得继续？ | `/jobs`、`/jobs/[id]`、`/scraper` |
| 材料 | 为当前机会准备什么材料？ | `/resume`、`/resume/[id]`、`/optimize`、`/studio` |
| 进展 | 已投递事项现在到哪一步？ | `/applications`、`/calendar`、`/email`、`/analytics` |
| 面试 | 下一场面试需要如何训练？ | `/interview`、`/interview/ai`、`/interview/pose` |

支持入口：

- `档案`：`/profile`
- `设置`：`/settings`
- `求职任务中心`：沿用 `/agent` 路由或后续重命名，但不作为与五段流程平级的业务模块
- `/resume/puck-demo`：开发/试验入口，不进入用户导航
- `/resume/print/[id]`：打印表面，不加载常规工作台外壳

### 3.2 今日行动队列

“今日”不是统计 Dashboard。默认排序：

1. 需要使用者确认的动作
2. 已阻塞或失败、需要处理的求职任务
3. 24–72 小时内的截止与面试
4. 正在运行的求职任务
5. 已承诺但尚未完成的下一动作
6. 主 Agent 建议的下一步

统计趋势进入“查看趋势”二级视图，不与行动队列争抢首屏。

## 4. WebUI 工作台外壳

### 4.1 桌面宽屏（建议 `≥ 1280px`）

```text
┌──────────────┬──────────────────────────────────┬──────────────────┐
│ 求职流程导航 │ 当前列表 / 表格 / 编辑表面       │ 上下文栏         │
│ 近期任务     │                                  │ 详情 | OfferU    │
│ 档案 / 设置  │                                  │                  │
└──────────────┴──────────────────────────────────┴──────────────────┘
```

- 导航默认约 224–240px，可折叠为 52–60px 图标栏。
- 中央工作区使用剩余宽度，避免统一 `max-width` 把数据表格压窄。
- 上下文栏建议 336–400px，可关闭；只存在一个右栏。
- 页面标题栏建议 44–52px，高度固定且可吸顶。

### 4.2 平板与窄桌面（建议 `768–1279px`）

- 左侧导航折叠为图标栏或临时抽屉。
- 中央工作区保持主视图。
- 上下文栏以覆盖式抽屉出现，但保留当前选中对象。
- 表格优先隐藏低优先级列，不把整张桌面表等比例缩小。

### 4.3 手机（建议 `< 768px`）

- 单列布局；五段求职流程进入底部导航或顶部切换器。
- 上下文栏变为全屏 sheet，提供明确返回。
- 手机只支持移动端轻操作：查看、确认、投递进展更新、回复主 Agent。
- 简历深度编辑和面试训练展示转到桌面/平板的明确说明，不渲染残缺编辑器。
- 触控目标最小 44px；桌面紧凑尺寸不能原样带到手机。

## 5. 标准页面模板

### 5.1 列表页面

适用：机会、投递、日程列表、求职任务、邮件、分析明细。

结构：

1. 紧凑标题栏：标题、当前视图、一个主动作、`…`、`询问 OfferU`
2. 视图栏：表格/看板/日历等视图，数量与筛选状态
3. 筛选栏：常用筛选外露，其余进入筛选面板
4. 数据主体：列表、表格或日历
5. 右侧上下文栏：对象详情或 OfferU

### 5.2 对象检查器

适用：岗位、投递尝试、日程事件、求职任务。

- 首段：对象名称、状态、下一动作
- 次段：关键属性
- 再次段：时间线、来源、关联对象
- 底部固定动作区：一个主动作和必要的次动作
- “完整编辑”进入全屏；不在检查器堆叠完整表单

### 5.3 专注模式

适用：简历编辑、面试房间、需要大画布的复杂工具。

- 自动收起全局导航与上下文栏。
- 顶部保留最小控制条：返回、对象标题、保存/运行状态、召回 OfferU。
- Agent 被召回时使用同一个上下文栏或覆盖式抽屉，不创建专属聊天实现。
- 离开前处理未保存变更；不得静默丢失。

### 5.4 求职任务视图

- 任务标题与状态
- 关联岗位、简历、投递、日程或面试
- 对话记录与工具执行摘要
- 待确认动作
- 证据与产出
- 固定输入区

“对话”是任务的一部分；“Agent Run”是任务的一次执行；它们不能在 UI 文案中互相替代。

## 6. Agent 交互统一

### 6.1 单一入口模型

- 删除右下角悬浮机器人。
- 删除“档案页自动切换另一套 Dock”的呈现逻辑。
- 页面标题栏提供统一 `询问 OfferU`。
- `Ctrl+K` 搜索、跳转并调用注册操作。
- Agent 输入框中的 `/` 只选择 Skill，不承担全局搜索。
- `/agent` 转为求职任务中心或统一 Agent 的全屏状态，不再维护另一套交互语法。

### 6.2 上下文契约

打开 OfferU 模式时必须携带：

- 当前路由与页面标题
- 当前选中对象类型和 ID
- 当前视图、筛选和排序摘要
- 未保存状态，但不能把未确认内容当成职业事实
- 可用 Operation 与数据授权

WebUI、机器 CLI、操作员 TUI 和斜杠 Skill 仍调用同一 Operation Registry；界面差异不能导致权限、确认、审计或错误语义漂移。

## 7. 视觉系统

### 7.1 色彩

- 浅色先行；本轮不交付深色模式。
- 中性灰白负责层级，现有暖红负责品牌与主动作。
- 成功、警告、危险分别使用固定语义色，不能拿模块品牌色替代状态色。
- 组件内禁止新增硬编码十六进制颜色；全部通过语义令牌。
- 不再使用红黄蓝绿区分不同业务模块。

建议令牌职责：

| 类别 | 令牌示例 |
|---|---|
| 画布 | `--canvas`、`--surface`、`--surface-subtle`、`--surface-hover` |
| 文本 | `--text`、`--text-secondary`、`--text-tertiary` |
| 分隔 | `--border`、`--border-strong`、`--focus-ring` |
| 品牌 | `--accent`、`--accent-hover`、`--accent-subtle` |
| 状态 | `--success-*`、`--warning-*`、`--danger-*`、`--info-*` |

### 7.2 字体与层级

- 页面标题：20–24px，600；不再使用 5xl–7xl 工具页标题。
- 区块标题：14–16px，600。
- 正文与表格：13–14px；中文行高 1.5–1.65。
- 辅助信息：12px；不得用极浅颜色代替层级。
- 数字列使用 tabular nums。
- 中文标签不使用大幅 uppercase tracking；当前 `font-bold uppercase tracking-[0.14em]` 只保留给确有意义的英文短标签。

### 7.3 密度

桌面采用“紧凑可读”，手机采用触控安全密度：

| 元素 | 桌面 | 手机 |
|---|---:|---:|
| 导航行 | 32–36px | 44–48px |
| 普通控件 | 32–36px | ≥44px |
| 表格行 | 40–44px | 转为卡片/摘要行 |
| 标题栏 | 44–52px | 48–56px |
| 常用间距 | 4/8/12/16/24px | 8/12/16/24px |

### 7.4 边框、圆角与阴影

- 默认 1px hairline。
- 小控件 6px；按钮/输入 8px；面板 10px；不使用满屏大圆角卡片。
- 页面分区优先使用间距和分隔线，不为每段内容套 Card。
- 普通表面无阴影；阴影只用于上下文栏、弹出层、拖拽对象和浮于内容之上的临时表面。
- 清理 `rounded-none` 与硬偏移阴影，但按页面切片处理，不做无法验收的全仓机械替换。

### 7.5 动作层级

- Primary：每个表面最多一个；使用暖红或高对比中性色。
- Secondary：中性边框或浅底。
- Ghost：默认无容器，hover 时显底色。
- Danger：仅用于真正破坏性操作，并要求确认或撤销窗口。
- 图标按钮必须有 `aria-label` 和可见 focus。

## 8. 动效系统

用户已确认：所有可交互项都有弹性反馈，但使用小振幅快回弹。

### 8.1 动效层级

| 场景 | 建议反馈 |
|---|---|
| 按钮/图标 | hover 轻微上移或放大，press 缩放至约 0.97–0.99 |
| 列表行 | hover 背景 + 1–2px 横向位移；选中态使用共享布局指示器 |
| 卡片 | 1–2px 上移或约 1.005–1.01 缩放，不叠加大阴影 |
| 上下文栏 | 透明度 + 12–20px 位移，使用可中断 spring |
| 导航折叠 | 宽度/布局连续过渡，内容交叉淡入淡出 |
| 任务完成 | 状态图标和结果区一次性回弹，不做持续庆祝动画 |
| 拖拽排序 | 直接跟手、松手回弹，并禁用文本选择 |

### 8.2 规则

- 禁止 `transition-all`；明确列出 `transform`、`opacity`、`background-color`、`border-color`。
- 普通 hover 优先 CSS；布局、手势和可中断弹簧使用现有 Framer Motion。
- 首个实施切片不同时迁移到新的 `motion` 包，避免把界面重构和依赖迁移耦合。
- 全局使用 `MotionConfig reducedMotion="user"` 或等价策略。
- `prefers-reduced-motion` 下移除位移、缩放和视差，只保留颜色与透明度。
- 取消当前所有页面统一 `y + scale` 入场；页面切换只保留必要的轻微淡入或共享布局连续性。

## 9. `Ctrl+K` 与操作发现

WebUI `Ctrl+K` 分为三组：

1. 搜索：岗位、公司、简历、投递尝试、求职任务
2. 跳转：五段流程、档案、设置、最近对象
3. 操作：从 Operation Registry 读取当前上下文可用操作

要求：

- 破坏性或需授权操作不能在命令面板中绕过确认。
- 无权限操作应显示原因，不静默隐藏。
- 键盘上下选择、Enter 执行、Esc 关闭，关闭后恢复原焦点。
- Agent 输入框 `/` 只展示 Skill Registry，不与 `Ctrl+K` 菜单合并。

## 11. 无障碍与交互质量门

- 所有图标按钮提供 `aria-label`。
- 输入、选择器和文本域提供真实 label 或 `aria-label`。
- 所有交互可用键盘完成，并有 `focus-visible` 状态。
- 异步保存、任务运行和错误信息使用 `aria-live="polite"`。
- 颜色不是状态的唯一表达；状态同时有文本或图标。
- 表格与列表处理长文本、空状态和加载状态。
- 模态框、抽屉和上下文栏管理焦点、Esc 与滚动锁定。
- 移动端不禁用缩放。
- 日期、时间和数字使用 `Intl.*`。
- 导航、筛选、视图和可分享的选中对象尽量反映在 URL 中。

## 12. 页面验收模板

每个迁移页面至少验证：

### 结构

- 首屏是否直接出现主要数据或下一动作
- 是否只保留一个主动作
- 是否使用标准标题栏、视图栏和上下文栏
- 是否删除营销式 Hero 和重复解释卡

### 渐进披露

- 列表选择是否进入统一上下文栏
- 低频动作是否进入 `…` 或 `Ctrl+K`
- 复杂编辑是否明确进入全屏
- Agent 是否复用同一 OfferU 模式

### 响应式

- 1440px：三段外壳不拥挤
- 1024px：导航折叠、上下文栏覆盖
- 768px：不出现意外横向滚动
- 390px：轻操作可完成，触控目标 ≥44px

### 动效与无障碍

- hover、press、focus、selected、loading、success、error 均有反馈
- 动效小振幅、可中断
- 减少动态效果下无位移/缩放动画
- 键盘焦点顺序稳定，关闭面板后焦点恢复

## 14. 技术边界与风险

- `@nextui-org/react` 已被官方弃用并迁移到 HeroUI，但不要把 HeroUI v3、Tailwind v4、React/Next 升级与首个 UI 切片绑定。先通过项目内语义组件收敛交互，再单独决定依赖迁移。
- 当前工作区已有大量用户改动。任何实施必须先明确允许修改的文件范围，不能覆盖或回滚现有改动。
- 新壳层不能复制业务 API 或直接写数据库；所有写操作继续通过 Operation Registry、确认门和领域 API。
- “求职任务”是新的用户可见聚合概念，不代表可以直接合并全局助手、档案、优化和面试现有会话表。
- 旧 Bauhaus 类名可以在迁移期间暂时保留，但其视觉职责必须被新语义令牌接管；不要为了改名制造一次无价值的大范围 diff。
