# Backend Operation Registry（ops.py）对抗评审 — 2026-09-19

## 结论（对照 Apple 上线水准一句话定性）

Registry 骨架（envelope / dry-run / 审计 / 幂等声明）设计严肃，但**确认授权是「按 surface 字符串约定」而非硬边界**：持久化提案→确认这条强路径有一个已证实的参数脱敏 bug（秘密参数被 `[redacted]` 重放）和一个提案状态机漏洞（被拒绝的 run 仍可确认执行）；同时存在第二套更弱的内存提案系统（web agent）绕过全部授权机制。离 Apple 上线水准还差一轮状态机收口与路径归一。

## Top-5 修复优先级

1. **OPS-01（P1）**：提案重放路径把秘密参数 redact 成字面量再喂给 op——`create_resume_share_record` 会生成「密码=`[redacted]`」的假成功分享链接；改 `_clean_action`/`_row_to_run` 不再 redact `args`（审计面独立 redact 已足够），或提案层用 ref 间接存取。
2. **OPS-02（P1）**：`reject_agent_run` 后 `confirm_operation_proposal` 仍可取出 `waiting_confirmation` step 执行——reject 必须终态化 step，confirm 必须先校验 run 仍 ACTIVE。
3. **OPS-03（P1）**：web agent 内存 `_PROPOSALS` 绕过全部授权/幂等机制且暴露全部 op——并入 `create_agent_run` 强路径 + web_agent surface 加 grant 白名单。
4. **OPS-07（P2）**：67 个 op 走无类型/无枚举的签名验证（含 `connect_imap_account` 这类带凭据的 mutation）——registry 注册处 assert mutation 必须有 `input_model`。
5. **OPS-04（P2）**：`surface` 自选字符串决定要不要授权——把「interactive 白名单」显式声明在 registry，未注册 surface 的 mutation 一律拒绝。

## 已达标的点（简短）

- `_claim_authorized_execution` 用 `OperationAuditLog.idempotency_key` 唯一索引做「先插入占位、撞键即查原行」的恰好一次语义，且对 `executing`/`failed`/`completed` 三态分别返回不同 envelope——并发/重放设计是认真的（`ops.py:5010-5107`）。
- 审计完整性是 fail-closed 的：审计写失败会包装 envelope 为 `ok:false` 并明示「副作用可能已完成需人工核对」，不假装成功（`ops.py:5141-5179`）。
- `_redact_mapping` 对 `audit_redacted_parameters` 做 sha256+长度占位而非纯遮蔽，审计仍可比对输入一致性（`ops.py:5196-5221`）。
- `_prepare_resume_optimization_after_pre_application` 的前置 stage 门 + `review_resume_optimization` 的 JD-hash/档案快照/调研快照三层 stale 检测 + `review_resume_proposal_item` 的 `workspace_snapshot_hash` 手工修改检测——提案新鲜度验证是真做了的，且 stale 后会落 `status="stale"` 留痕。
- routes 层除 `scraper.py` 两处维护性 UPDATE 外全部经 `execute_operation`，未发现绕过 Registry 直写业务表的残留路径；`JobIngestItem`/`_StrictOperationInput` 普遍 `extra="forbid"`+pattern+范围约束，schema 校验质量不错。
- `execute_confirmed` 对中断在 `executing` 的 step 标 `uncertain`+`needs_reconciliation` 拒绝自动重放，是教科书式的副作用不确定性处理。
