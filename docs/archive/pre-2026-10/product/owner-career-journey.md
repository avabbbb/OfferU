# 真实求职用户的完整体验与验收契约

状态：**CURRENT PRODUCT DETAIL / OWNER ACCEPTANCE TARGET**
更新：2026-10-02

这是用户本次明确要求的产品细化，遵循 [GOAL](../../GOAL.md)、[当前产品定义](./current-product.md) 与 [主动职业总监](./proactive-career-director.md)。本文定义应有体验，**不表示这些功能已经实现或通过内测**。当前实现核对见 [能力审计](../evals/reports/2026-10-02-owner-journey-capability-audit.md)，交给测试 Agent 的两个任务见 [内测 Goals](../evals/OWNER_DOGFOOD_GOALS.md)。

## 1. 用户到底在使用什么

用户把 OfferU 当作持续协作的求职工作台：已有简历、职业经历和目标被整理成看得懂的 Profile；岗位被研究、评分和排序；用户选出今天要推进的岗位；每份定制简历的修改可检查；真实投递、沟通、面试准备和复盘互相联动；隔几天回来仍知道发生了什么、还差什么。

Desktop 负责展示、编辑、复核、采用和长期保存。当前 Agent 负责研究、访谈、判断和撰写；内置 Agent 与用户自带 Agent 使用同一 Career Truth、Registry 和工作区。换 Agent、关聊天、重启应用都不丢失已接受的工作。

完整旅程：

```text
安装 Desktop / 从已有 Agent 的 OfferU Skill 开始
→ 安装准备与真实连接回读
→ 有简历导入；无简历通过对话采集
→ 授权后读取选定的 Agent memory / 工作资料
→ 可见、可编辑、可核对来源的 Profile
→ 官网 / 已授权 BOSS 岗位发现、去重、评分、排序
→ 用户选择今天推进的岗位
→ 共性能力 × 目标独特点 × 本人证据
→ 有来源、有修改理由的岗位化简历
→ 用户审核、导出、准备与授权投递
→ 邮箱 / BOSS 进展候选 → 用户确认 → 同一投递时间线
→ 分轮面试准备 → 真实面试 → 逐题复盘
→ 审核学习候选 → 下一次准备与 Profile 演进
→ 再次打开：刷新、解释变化、处理过时信息
```

## 2. 初次使用要轻，Profile 要扎实

首次必需成果只有安装可用与有来源的 Profile；Agent 接入不阻塞首次价值。首个 Job 可以立即进入工作区，但邮箱、BOSS、浏览器工具和高级自动化按使用时机配置。

| 时机 | 用户体验 | 验收结果 |
| --- | --- | --- |
| 已下载 EXE / DMG | 安装并打开，应用负责 Runtime | 不要求用户装 Python、Node、Git 或启动前后端 |
| Skill 已安装，Desktop 未安装 | Agent 识别缺少产品，依据可验证官方发行物指导安装；自动下载/启动仅限确有支持的安装契约 | 不寻找源码 checkout 冒充安装；缺少安装能力应明确报缺口 |
| Desktop 已安装 | 发现宿主、准备 runtime-bound Skill、完成真实只读回读 | 区分发现、安装、连接验证和真实职业任务成功 |
| 有真实简历 | 在用户指定目录内发现候选文件，展示文件和用途，再读取选定内容 | 不全盘扫描；不上传未授权内容；原文件保留 |
| 没有简历 | 以一问一答访谈建立初始档案 | 不把空白默认档案说成已建档；不逼用户先写简历 |
| 有 Agent memory | 明确选择记忆来源、范围和用途，预览相关片段 | 不自动读取全部会话或凭据；来源是观察/候选，未经复核不是事实 |
| 首次同步邮箱或 BOSS | 在这个功能内解释收益、授权、登录和撤销 | 不用一长串技术配置阻塞建档 |
| 首次需要浏览器协作 | 检查实际工具能力，缺少时通过支持的安装路径补齐 | Skill 本身不是浏览器；装好 Playwright 不等于支持某招聘网站 |

用户口述的“学习 / 工作 / 浏览”只描述了目录结构，尚未提供精确绝对路径。测试 Agent 应询问或由用户选择目录，不能猜路径并遍历整个磁盘。

Profile 应逐步覆盖：目标岗位与方向、求职阶段、教育和工作经历、项目和作品、真实职责和 ownership、成果及证明、技能及使用场景、原有简历表达风格、地点/薪酬/时间偏好、明确避雷项、尚待核对的矛盾与信息缺口。学校和社招分别按 Strategy Pack 判断，不用通用百分比完整度。

访谈依据具体任务追问“做了什么、你承担哪一部分、结果是什么、证据在哪里”，而不是让用户自评能力；不知道数字就保留未知或定性表述，不逼出一个估算数字冒充事实。全面是长期积累的结果，不是第一屏问完所有问题。

Profile 页面必须让用户直接看到：已确认内容、待确认内容、来源、缺口、目标相关的 strong / weak / missing / unknown / under-expressed evidence、这次新增或更新内容，以及下一步。建档结束时必须说明实际写入了什么、哪些尚未确认。

## 3. 联网、Ask 与采用审核

用户最新纠正：**Fresh Reality 与 Interactive Agent，不机械要求每句话搜索和 Ask。** 依赖当前岗位、公司、团队、招聘、薪酬、ATS、面经或产品业务现实的判断必须刷新信息，或明确说明无法刷新；保存来源、日期及适用范围，求职者事实仍来自本人证据。

当用户的信息、定位、偏好或取舍会显著改变结果时，使用原生 Ask，一次尽量一个有效问题；已经明确的决定继续执行。工具不可用或后台无法交互时，把真正必要的问题送回用户，不能假问、假回答或假联网。不因交互规则建立第二个 Agent 循环。

Ask 答案不批准尚未展示的简历改写、职业事实写入或站外发送。用户应能审核已展示的一段或整份具体改动集合；允许有界聚合审核，但保留逐项证据、事实门、版本检查与审计。读信息、准备草稿和内部配置检查自主推进。

一次简历若迫使用户审核 50–80 个独立 Proposal，直接判 UX BROKEN。期望介入集中在定位/结构、经历取舍、section before-after 和最终简历；内部 mutation 可逐项审计，不等于用户要逐项点击。

## 4. 找岗位、评分、排序和选择

来源包含目标大厂官网、支持的公开招聘源和用户授权的 BOSS 能力。每条候选展示来源、采集时间、原链接、是否仍有效、重复归并结果和缺失信息。每天推荐必须实际获得新数据；仅对旧库重新排序应标记为旧库评估。

评分用于帮助排序，不是预测录取概率。评分维度、权重和证据必须可展开：硬条件、职责/能力匹配、可验证经历、目标独特点、个人偏好、已知风险、信息新鲜度与不确定性。信息不足应解释影响，不能给固定假分或把未知当零分。用户改变目标后排序能解释变化。

用户逐个或按组选择“今天推进 / 暂缓 / 不考虑”。选择“推进”只启动研究和材料准备；不自动代表已投递。当天推荐展示少量最值得处理项及 why_now，不重复骚扰已经拒绝、已过期或长期忽略的建议。

自动发现与每日评估沿用 `AutomationEvent → AutomationRule → CareerTask → Agent/Runtime → Operation`，有来源范围、预算、去重、暂停和失败展示；不能仅靠一个定时脚本写死职业推荐。

## 5. 岗位研究同时服务简历与面试

研究以目标 JD 为中心，比较可比的公司、岗位族与 seniority，避免将相邻但不同岗位混成目标岗位本身。保留每个对照 JD、时间和来源；样本不足、页面无法访问和岗位身份未知都展示为缺口。

用户应看到三组结果：

| 结果 | 依据 | 如何使用 |
| --- | --- | --- |
| 同类岗位共性能力 | 可比样本中实际出现的要求与计数 | 简历基础表达和面试基本功 |
| 目标岗位独特点 | 目标 JD 明确表达、与可比样本不同的要求 | 有证据的重点经历与专项练习 |
| 本人证据与缺口 | 原简历、已确认 Profile、项目/经历来源 | 可以突出、需要补证、暂时不能声称的内容 |

Runtime 负责 cohort、去重、统计和 Delta；Agent 收集与解释。不能由模型或采集 worker 捏造市场比例；“反复出现”也不自动证明是所有公司的必需能力。

同一 Job Workspace 内保存公司和团队研究：事业群、部门、业务、职责、团队结构、招聘流程、工作节奏、已知招聘者/面试官信息。未知偏好不是事实；公开来源、本人沟通记录、社区单一信号和推断分别标记。不要为这一展示新建另一套业务状态。

牛客、小红书和公开简历只提供带时间、岗位和来源的参考信号。简历表达参考提炼匿名模式，不复制他人的身份、雇主、成绩、证书或完整简历；不把他人成果写进本人材料。

## 6. 定制简历必须每次可检查

先读完整 Profile、原简历风格和目标 Job，再通过 Ask 确定定位、结构和经历取舍。每个重要改写包含 Before、After、Why、目标要求、本人证据和事实门状态；共性能力与目标独特点在改写理由中可对应。

Desktop 必须展示逐段对比、已生成/未生成/失败/待审核/已采用的状态，允许拒绝、编辑后接受、接受一段或已展示的整份改动。实时进度和适度视觉突出帮助辨认新增结果，但动效不替代文字状态，照顾 reduced-motion 和键盘访问。

不得新增无来源的数字、技术、公司、职责范围或成果。保留原始版；人工修改使旧 Proposal 过期；重新生成要展示版本关系。导出的 PDF 对应用户实际采用的版本。外部 Agent 草稿返修仍交回原 Agent，不在后台悄悄换一个模型替用户重写。

## 7. 投递、登录、注册和 BOSS 联动

用户进入相应功能后再要求邮箱授权、平台登录、手机号/验证码和浏览器准备。验证码与账号操作由用户按实际页面完成，凭据留在支持的安全存储；“需要信息”必须是具体下一步，不让用户先理解工具栈。

协助填写、账号注册、最终提交、消息发送分别验收。**自动注册是单独的外部动作需求，现阶段未被已有投递预演证明支持。** 每项必须有真实可用的 connector、具体内容预览、必要的用户授权、结果回读和失败处理；没有合法执行路径就展示缺口，不能绕开 Registry 在浏览器里偷偷执行。

BOSS 能力应逐项核对上游 schema、本机版本、OfferU 适配、用户账号和 Desktop 结果：搜索、个性化推荐、详情、本人简历、投递列表、面试邀请、沟通过的 BOSS、聊天读取、跟进、重新联系。招聘者下载候选人简历不等于求职者读取本人简历。

邮箱/BOSS 信号先关联到正确 Job/Application，再形成进展候选；未关联、模糊或冲突的记录留在待审核区。用户确认后才改变阶段，多次同步不产生重复投递、面试或事件。

简历更新和到期跟进应生成 re-engagement candidates，解释 why_now，关联最新材料和历史沟通。重新联系需求保留，但当前默认只准备待审核候选/草稿；重复招呼是否可发送须按实时平台能力验证，不能把首次 greet 或重复运行成功当成支持。任何未来自动发送还需另行产品授权、有界名单、频率、去重、拒绝/冷却、审计与暂停，不因用户海投就推断无限许可。

## 8. 分轮准备、逐题复盘和正向反馈

准备读取：岗位共性/Delta、本人 evidence gap、当前面试轮次、团队研究、前几轮和其他已审核面试学习、近期带来源的面经。显示这些信息具体改变了哪些练习，而不是泛泛输出题库。

| 轮次 / 对象 | 反问与待确认事项示例 |
| --- | --- |
| HR / 招聘沟通 | 后续流程、预计时间、下一轮形式与关注方向、部门归属、岗位 level 和信息缺口 |
| 一面 / 技术或业务面 | 实际任务、现有问题、技术/业务约束、团队协作与成功标准 |
| 二面 / 负责人 | ownership、跨团队关系、优先级、资源与决策权、前一轮待核对事项 |
| 后续轮 / offer 阶段 | 汇报关系、工作节奏、评价机制、成长空间、尚未澄清的条件 |

这张表是问题用途示例，实际选择由 Agent 结合轮次与上下文决定，不硬编码所有公司相同流程或面试官喜好。

复盘先读取真实 transcript；没有记录则 Ask 用户回忆，明确标注 recall、遗漏和不确定性。逐题保存：原问题、实际回答、追问/反应、考察能力、做得好/薄弱处、依据、改进答案和练习建议。建议答案与当时实际回答分开，不能倒写成用户已经答过。

复盘同时更新待核对的团队/流程信息、后续安排、题目频次、故事素材和弱项。学习先进入 Candidate，审核后用于下一轮；撤回、不可信或过时的 claim 不再被引用。下一次准备必须展示“因为上次这道题/这项不足，今天增加这项练习”的引用链。

真实面试不能靠测试 Agent 编一个经历代替。没有真实记录时可做明确标记的演练，但真实面试复盘与长期反馈验收保持 NOT_RUN。

## 9. 几天后回来与两条数据整理路线

“更新程序”“刷新来源数据”“整理旧历史”“删除业务数据”是四种不同动作，Desktop 需要让用户看懂。刷新展示上次时间、此次新增/变化/失效项、失败源和待审核冲突；不能用成功 toast 把旧数据说成最新。

| 路线 | 应有体验 | 必须保留 / 验证 |
| --- | --- | --- |
| 全清重新开始 | 展示将清理的当前 OfferU 业务数据和文件范围，备份可恢复后独立确认 | 保留账号/Key、安全记录、备份和审计；不删除原简历、用户工作文件或外部 Agent memory |
| 蒸馏为历史节点 | Agent 将选定过时上下文整理成短摘要，展示预览与原来源，用户接受后归档 | 保留已确认职业事实、投递结果、证据链接、时间范围、修订/撤回历史和恢复/展开路径 |

对话压缩和 Memory Inbox 候选蒸馏不等于整个业务历史的可恢复归档。清除缓存也不等于清空 Profile。测试必须核对新旧 Agent 会话、索引、浏览器本地状态和文件产物，不把“数据库为空”当成新用户环境已干净。

## 10. Skill 生态与实施顺序

OfferU 总 Skill 负责识别目标与读取 live catalog；功能 Skill 负责方法与最小工具范围；每个功能初始化说明所需信息、依赖、授权和失败恢复。首次只准备当前必要能力，不一次安装整个生态。

允许组合已经发现的建档、简历、调研、浏览器和面试 Skill；它们提供方法，业务结果仍经 OfferU Registry 落到同一个 Profile/Job/Application。是否独立建立 Skill 仓库属于后续分发选择，不是本次内测前置，也不能引出另一套状态。

本次已核对的阿酥参考为 Hisn00w/ASu-skills，当前由 registry 管理多个功能入口。具体源文件和 OfferU 映射见 [阿酥及其他 Skill 研究](../evals/reports/2026-10-02-career-skill-reference-review.md)。重点验收跨 Skill 的事实/候选表达/来源/个人边界连续性，授权工作记录中的本人、Agent 与团队动作区分，匹配中的表达缺口/证据不足/真实缺口，以及依据真实回答的变体复练。竞品方法不自动授予 OfferU 站外能力或权限。

实施按纵向切片推进：安装与清洁环境 → 有/无简历可见建档 → 一批真实岗位排序 → 一个 Job 的研究及逐段简历审核 → 一个来源的进展同步 → 一次真实面试反馈闭环 → 再访刷新/整理。每一片独立保留证据，不用规划数量替代可用程度。

## 11. 开始真实测试前的最终验收口径

OfferU 是 Skill 生态驱动的 Career OS；用户感知一个 OfferU，顶层 router 根据 intent、Career State、Job、可用工具与已安装第三方 Skill 组合功能。Career Ops 当前也使用顶层 mode routing 与 plan/practice/debrief 等模块，并维护 story-bank、question-bank 和岗位 prep 资产，见其 [router](https://raw.githubusercontent.com/career-ops-hq/career-ops/main/.agents/skills/career-ops/SKILL.md) 与 [plan](https://raw.githubusercontent.com/career-ops-hq/career-ops/main/modes/interview/plan.md)。第三方输出仍须 OfferU 的 provenance、验证、持久化与用户决策，不创建第二套职业事实。

Desktop 是 Career Operations Cockpit。Profile 展示完整职业证据及 unknown/correction/learning，不止解析简历；Job Queue 可排序且解释硬条件、level、地点、目标和风险；Role Intelligence 展示 comparables、table stakes、独特点、Evidence Map 与 unknown；Resume 展示版本、section diff、why、采用/拒绝与当前 Job 使用版；Application 分开 prepared、form filled、reviewed、submitted、receipt verified；Interview 展示轮次、对方 intelligence、重点、反问、历史问答、表现和下一轮学习。这些是语义验收状态，不要求新建另一套数据库枚举。

同一个高优先级 Job 的结构化 Role Benchmark 必须同时驱动简历和面试，验证 asset ID/版本/来源一致，而不是两次聊天分别做研究。面试准备还须读取实际 submitted Resume Version、历史 question/story bank 与审核后的 weak areas。HR/HM/Peer/Final 的反问由当前团队/流程 unknown 动态生成，得到的回答作为有来源候选回写同一 Job intelligence；不推测具体个人私密偏好或人格。

BOSS 按 upstream / OfferU integration / owner acceptance 三层逐项测试候选者 search、detail、recommendations、applied、interviews、chat、greet、batch-greet、apply 和 pipeline。recommend 不能视作稳定核心链路，优先依赖 search/detail 并核对实际 schema/可用状态；上游已有而 OfferU 未接，标 `NOT IMPLEMENTED IN OFFERU`。re-engagement 结合已沟通/投递、last contact、岗位开放、简历重大更新及回复，保留 cooldown、dedupe、last-contact、outcome；新岗位 greet 与旧岗位 follow-up 不混同。无 connector 则准备文本或明确的用户接管路径，不能伪装已发送。

普通长期用户 Distill & Continue 保留 decisions、evidence、outcomes、lessons、已采用 Profile 改动和 receipts，归档重复临时状态后刷新外部现实；升级不要求全清。Owner Clean Reset 才准备隔离初态或有备份的独立确认清理。
