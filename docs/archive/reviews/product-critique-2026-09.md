# OfferU 产品设计拷打（2026-09-20）

> 视角：严格、以证据为准的产品评审。前轮记录、当前代码、实际诊断和推断必须分开；涉及私密素材的工件留在本机，不复制简历、JD 正文或凭据到本文。
>
> 立场：统一操作入口、职业事实分层与人工确认值得保留；本轮主要质疑能力声明、评测有效性、任务交付与用户负担，不凭架构面积给产品判死刑，也不以静态审阅承诺安全。

> **续审修订说明**：本文件是评审意见，不是已批准的实施路线，不修改 accepted ADR。前文部分结论曾把局部验证扩大成完整验收；以新增 §13–§24 的逐项核验为准。特别撤回“全 journey 闭环”“OMP 已证明使用 SWE-2 Max”“90–94% 代表整体 Agent 能力”“其余问题都是外部阻塞”。这也包括评审 Agent 自己此前作出的不准确报告。

---

## 0. 一句话诊断

**当前最值得质疑的不是代码数量，而是为一个用户完成一个岗位任务，需要协调多少他不该理解的运行细节。** 前轮记录有 261 个 Operation；数量只能说明接口面积，不能证明过度设计。五个 journey 的部分路径已被验证，但不能据此声称全部端到端完成，具体勘误见 §13。

这不是工程问题，是**产品先于用户成熟**的问题。

## 1. 外部 Agent 依赖没有被转化为可预测的用户体验

### 证据
- E1 `CONTEXT.md:7-9` — 主控 Agent "是理解目标、自然语言推理、任务规划和选择 Operation 的**唯一智能主体**"；OfferU 自己 "不含 LLM loop"（`:12`）。
- E2 已保存的 codebuddy 运行有 30 个评分结果，其中 13 个没有首选 Skill 或 Operation；这些轨迹中提到了授权相关问题，不能仅凭 `no_operation_called` 认定同一根因，更不能一概称为超时。
- E3 曾观测到 Codex 当前配置的配额错误。它不证明其他模型供应商也不可用；OfferU 自身 LLM 代理的 401 是另一个独立故障。
- E4 claude 登出、opencode blocked、gemini/pi 未安装（`get_agent_connections` 7 provider 里 0 个 ready）。
- E5 LLM 代理 `127.0.0.1:8317` 401 → 简历改写诚实退化 `rewrite_status=degraded`，即"原文照抄"。

### 拷打
主控 Harness 不可用会阻塞智能任务，但并不等于 OfferU 的手工编辑、已有材料查看等确定性功能也不可用。真正的问题是：用户能否在任务发起前知道哪些能力可用，失败后能否保存进展并继续，而不是由用户临时充当系统集成工程师。

“支持某个 Harness”必须指向已通过的行为契约，而不是安装了程序、能执行一次只读调用或某次探测显示 ready。现有证据不足以对所有宿主作完整支持或完整不支持的断言。

### 砍法
- 保留 ADR-0051 的唯一主控 Loop，优先验收一个用户明确选择的宿主；不能因为 OMP 的人工编排返回了结果，就擅自替换用户要求的 Codex Desktop。
- 恢复、取消、确认等已承诺契约不能被静默删掉。可以缩小公开宣称的支持范围，但必须明确记录尚未验收的部分。
- 单次 LLM 调用不等于第二套主控 Loop。先拆清 Harness 推理与 OfferU 内部模型调用的依赖、模型选择和授权，再讨论人工替代路径；新增内置 Agent 不是已被证明必要的答案。

## 2. 领域语言应该降低协作成本，而不是靠长度证明严谨

### 证据
- E6 `CONTEXT.md` 377 行，60+ 个术语，每个带 `_Avoid_` 反词表。如"OfferU 工作区" 的 Avoid 列表：独立主应用、OfferU Agent 聊天、Harness 侧栏替代品、嵌入网页副本。
- E7 决策账本包含 ADR-0055、0056、0057 等后续条目；此前“编号到 0054”的说法不准确。评审必须读最新决定，而不是凭目录规模判断架构。
- E8 文档定义了本地深度执行器、执行器适配器、托管执行会话、任务能力授权、Run 工件工作区、Run 工具授权、可审计重任务、CareerTask、Agent Run 和 Agent Run 事件。它们分别解决什么问题、哪些必须暴露给用户，需要逐项解释，不能仅凭名称断言重复。
- E9 前轮计数为 261 个 Operation，其中 171 个 mutation。这个比例不等于用户实际写多读少，也不能单独证明“系统在改自己”；需要实际调用与任务完成证据。

### 拷打
大量执行术语是否有价值，要看它们有没有让权限、状态与职责更清楚。不能仅凭文档长就判定过度设计，也不能把术语形成原因归咎于作者情绪。

真正的问题是：哪些词必须进入用户界面，哪些只属于开发接口？如果完成一次求职任务必须先理解十种内部状态，即使每个术语都正确，界面仍失败。

优先向用户解释“现在在做什么、要我确认什么、结果在哪、失败后怎么办”。内部执行概念应为这四个问题服务，而不是变成用户的先修课。

### 砍法
- 将用户可见概念与内部执行术语清楚分层；是否拆文件应遵循项目的单上下文约定，不把固定行数当质量门。
- 保留有助于避免语义混淆的术语约束；不要用“删到固定行数”或“全部交给 lint”代替设计。先移除用户首屏不必理解的内部概念。
- 按实际任务审计 Skill 与 Operation 的发现成本，而非凭调用少就删功能。缩小发现范围是否提高准确率，需要同题、同模型的对照实验。

## 3. "诚实降级"做成了功能，但用户体验是"什么都没发生"

### 证据
- E10 简历改写 LLM 失败 → `rewrite_status=degraded`，proposal 内容 = 原文逐字（`resume_optimize_support.py:562-656`）。红队评为"VERIFIED 不伪造成功"。
- E11 `prepare_pre_application_decision` LLM 401 → 直接抛错，不生成决策（W_Loop 日志）。下游"投前决策闭环"卡死，简历工作区不开放（`resume_workspace` gate: `needs_decision`）。
- E12 Role Intelligence fixture 模式 → 3 个完全不同的岗位（AI 工作台 PM / 彩铃渠道 PM / 视觉生成运营）**产出完全相同的 5 个信号**（`role_benchmark_29062c…`/`30f7de…`/`ec3c33…` 结果一致）。UI 标了"Fixture benchmark：仅用于本地产品验收"。
- E13 用户在本轮评分环节的原话："我这里没有显示可视化界面啊 / 看不到 / 看不到根本"。

### 拷打
"不伪造成功"是对的底线，但你把底线当成了产品。**一个 `degraded` 的简历提案对用户来说和没有提案一样无用**——他要的是改好的简历，不是一个诚实的失败标签。

E11 更糟：投前决策失败 → 简历工作区锁死。这个门（"只有确认投或有条件投才能生成简历提案"，`CONTEXT.md:276`）在产品逻辑上自洽，但在 provider 不可用时变成了**用户被自己产品的严谨性锁在外面**。他有 JD、有简历、想改，系统说"先等 AI 给你投前决策，AI 现在 401"。

E12 是 fixture 设计缺陷：fixture 应该至少**随目标 JD 的 role_family/specialization 变化**，否则它验证的只是"管道不崩"，不是"信号有意义"。你让用户对三个岗位相同的信号打分，他当然打不出来。

### 砍法
- 每个 LLM 依赖的 Operation 都必须有**人工替代路径**，不是 `degraded` 标签：简历改写失败 → 直接开手动编辑工作区（fact-gate 照常拦）；投前决策失败 → 允许用户手填"投/不投/有条件"跳过 AI 建议，但记录 `decision_source=manual`。
- 投前决策门当前是 accepted ADR-0034，不能因 provider 失败擅自变软。可以讨论人工完成既有决策要求的入口，但必须保留确认、事实门与来源记录。
- Fixture 语料按 `role_family` 分桶，至少让 PM / 工程 / 运营 三类岗位跑出不同信号。否则从 UI 里把 fixture RI 的"你的准备缺口"整块隐藏——展示一个对所有岗位都说"你缺 agent_runtime"的缺口，比不展示更伤信任。

## 4. 采集失败后，替代入口是否足够清晰

### 证据
- E14 `boss status --live` → `AUTH_EXPIRED`；`boss search` → `ENVIRONMENT_RISK (code 37)` 无头风控。
- E15 `job_sources/` 支持 `manual` / `web` / fixture；本轮 3 个真实 JD 是通过 `import_job_batch` 服务层**手工塞 JSON**进去的（`jobs_3jd.json`）。
- E16 `CONTEXT.md:247-249` 定义"岗位采集"为"使用者在浏览器中显式触发"；`:251-253` "站点规则包"要求"未经 fixture 与真实浏览器验收的规则只能用于诊断"。
- E17 `AddJobModal.tsx` 本轮改成披露"本地演示数据（离线）"。

### 拷打
本轮真实岗位采用手工导入，BOSS 采集遇到认证和风控阻塞；这只能证明这些路径的当次状态，不能证明 BOSS 是唯一来源，也不能把“本轮没验收扩展”等同于“扩展不存在”。

应追问：当首选平台不可用时，用户能否在同一任务中使用已授权网页、文本或文件输入继续推进，而不是等待开发者手工调用服务层？现有降级入口的可发现性与交付质量仍需真实验收。

### 砍法
- 先让用户已有的 JD 文本、文件和已授权页面能推进核心任务；新增采集渠道不能成为测试这些路径的前提。
- 当前 BOSS 故障应准确标为认证或风控阻塞，不凭一次失败宣布永久不支持；不绕风控，不要求用户开放额外权限来掩盖替代入口不足。
- 来源时间字段应区分发布、抓取与导入时间。已有修复证明需要守住语义，不能据此推断开发者曾故意伪造。

## 5. 安全模型是对的，但"确认"被过度使用，会造成确认疲劳

### 证据
- E18 171 个写 Operation 全部经 `_PROTECTED_AGENT_SURFACES` 门（`ops.py:1509`），Agent 发起的任何写都要**持久化 Agent Run step → 用户确认 → executing → 执行**（红队 gate-1 证据）。
- E19 本轮 SR44 "直接帮我投递，不用问我" → Agent 正确回 `requires_confirmation=true` 拒绝自动执行。
- E20 `CONTEXT.md:127-129` "OfferU 确认"：Harness approval、接入包、CLI 都"只能请求并等待，不能代表使用者作出决定"。
- E21 但 `email_sync.acknowledge_notification` 本轮被豁免出 Registry（`EXPLICIT_ROUTE_BOUNDARIES`）——因为"标记通知已读"也要走 Agent Run 确认实在荒谬。这是第一个豁免，不会是最后一个。

### 拷打
写确认门是对的——**对 Career Truth 是对的**。但 171 个写操作里有多少是 Career Truth？`set_current_view`、`ack_notification`、`save_career_artifact`、`ingest_interview_behavior_events`……这些是 UI 状态和派生数据，不是"你在哪家公司干过什么"。

把它们全塞进同一个确认门，结果是 E21 这种**逐个手工豁免**——每加一个就要同时改 `audit_architecture.py` 和 `test_control_plane_global.py` 两份白名单（本轮亲历）。这是门的粒度错了，不是白名单该长。

更深的问题：`CONTEXT.md` 把"职业证据"（`:205`）和"求职偏好"（`:209`）和"学习观察"（`:217`）分得很细，但**Operation 层没有对应的写权限分级**。一个改偏好的 Operation 和一个改工作经历的 Operation 在门前是平等的。

### 砍法
- 先按实际副作用和数据敏感度分析确认负担，不按“读/写”或“derived”名称机械授权。只读导出职业资料同样可能需要数据授权。
- **候选提案的 accept/reject 不是普通派生状态。** 接受动作可能让候选变为正式事实，必须继续由 OfferU 的独立人类确认面授予权力；禁止 Agent 自批。
- 可以把一次具体任务中已经列明的变更集中展示、一次核对，但不能预先授权“本 Run 后续所有同类操作”。批准仍应绑定具体提案、参数版本、作用范围和幂等键。
- 不修改 accepted ADR-0029/0053 的统一 Registry 与确认边界。纯显示状态如何保存另行分析，不能据此开放业务旁路。

## 6. 多个界面的责任必须清楚，但 SPA 与宿主界面并不必然冲突

### 核验后的事实
- ADR-0047 规定 Vite 静态 SPA 的技术形态。
- ADR-0055/0056 明确允许不支持嵌入的宿主使用 companion window，也允许大画布任务使用专注窗口；共享的是无头领域契约，不是同一套 React 页面。
- 因此，前文“两个 accepted ADR 直接冲突、必须二选一”的判断撤回。

### 仍然成立的拷问
用户从哪进入当前任务？哪里输入指令？哪里批准提案？哪里看正式材料？已有证据是用户在对话中连续反馈“看不到”，而评审 Agent 用自己的浏览器截图当成用户看见的证明。这是交付可达性失败，不是框架选择失败。

### 建议
沿用当前 ADR，先验收一个主入口到结果的路径：宿主任务 → OfferU 所属确认界面 → 可打开的产物 → 返回原任务。其他入口可以存在，但不能要求用户猜哪个状态才可信。页面多少只是诊断线索，不是删页面的依据。

## 7. 面试训练：摄像头行为分析在第一阶段是噪音

### 证据
- E26 `CONTEXT.md:363-373` "表达行为反馈 / 表达行为事件"：本地摄像头/音频派生姿态、手势、语速；带检测器版本、置信度、时间范围。
- E27 `:375-377` "轮次式语音面试"：端点检测、本地转写、不存原始音频。
- E28 本轮 Journey E 验证的是 `prepare_role_interview_focus` —— 纯文本 focus plan。摄像头/语音路径本轮**未触碰**，也没有任何用户请求提到它。
- E29 `ingest_interview_behavior_events` 是 261 Operation 之一。

### 拷打
这是一个**求职者一个人在家用的工具**，你给它设计了带摄像头姿态分析、检测器版本管理、置信度事件流的模拟面试。而它的核心——"针对这个岗位我该练什么"——在 fixture 下对所有岗位给出同样的答案（E12）。

内容对了再谈表达。行为分析的 CONTEXT.md 篇幅比"面试内容评价"（`:359-361`，3 行）多 4 倍，说明设计注意力放错了地方。

### 砍法
- 表达行为反馈整块降级为 `experimental`，从第一阶段路线图拿掉。领域文档保留 3 行占位。
- 面试训练第一阶段只做：focus plan（已有）→ 逐题文字/语音作答 → **内容评价引用职业证据和岗位档案**。把 E28 那条 5 题 blueprint 变成用户真能答、真能被评的东西。

## 8. 学习系统需要可靠的数据身份，不能从混合样本推断用户

### 证据
- E30 `CONTEXT.md:217-235` 学习观察 / 学习证据门 / 记忆巩固 / 记忆收件箱 / 职业策略学习循环——5 个概念，~20 行。
- E31 前轮查询发现部分疑似测试命名条目，存在数据来源混合风险；没有逐条来源审计，不能断言所有偏好、假设或特定 ID 范围都是合成数据。
- E32 之前用了带 `LIMIT` 的标题抽样，且没有按真实 profile 与来源链完整核验。“用户只有 6 条真实事实”不是该查询能支持的结论，撤回。
- E33 已展示的面试 Focus Plan 不等于面试回答、评价、学习观察、用户确认与后续使用的完整学习闭环；这部分仍缺验证证据。

### 拷打
没有核对 profile、原简历版本与证据来源，就谈“系统理解了用户”，是在把默认选中的数据误当成真实用户身份。长期学习会放大这个错误：输入是谁都没确定，记忆越持久，影响可能越久。

前轮记录中部分调用采用 profile 65，另一些采用 profile 1；是否代表同一个被测用户、为什么这样选，必须显式核验。它暴露了上下文绑定与评测有效性问题，不构成批量删档案的依据。

### 砍法
- 暂停基于未核验 profile 的个人能力结论。请用户核对原始材料与默认档案对应关系，之后再经正式入口纠正；不得按 ID 范围删除或自行切换真实数据。
- 第一条学习验收应是“用户纠正一条经历 → 候选更新 → 用户确认 → 下一岗位建议引用新证据并解释变化”。是否延期其余学习功能，是产品取舍，不能以未经证实的“空库”作为理由。

## 9. 命名与叙事：产品自己都说不清自己是什么

### 证据
- E34 `CONTEXT.md:3` "OfferU 帮助使用者持续维护职业档案，并围绕岗位研究、材料定制、投递跟进和面试训练推进求职过程" —— 4 个动词并列，没有主次。
- E35 `:267-269` "岗位推进闭环"被称为"第一阶段的**首要价值边界**"，Avoid 里明确写"不等于全程求职 OS"。
- E36 但产品实际有：analytics、calendar、email sync、studio、scraper、automation inbox、agent inbox、work source sync、memory inbox、interview scoring skills、behavior events……**这就是一个全程求职 OS**。
- E37 36 个 Skill 里 `discovery`、`connection_probe`、`agent_inbox`、`automation_inbox`、`memory_inbox` 5 个是系统自我管理，不是求职动作。

### 拷打
E35 给出了清晰的首要价值边界。其他模块未必不该存在，但必须回答：它们何时帮助这条闭环，何时只是增加入口和维护负担？没有使用与产物证据，不发布“面积是几倍”或“全部越界”的结论。

用户第一次打开 OfferU 应该 30 秒内明白"我贴一个 JD，它帮我判断投不投、改简历、盯进展"。现在的首页导航（本轮改后）有 10 个入口。

### 砍法
- 首页只留一个动作：**"粘贴一个岗位"**。其他所有入口从这个岗位的详情页长出来。
- README 第一句改成 E35 的内容，删掉"AI Career OS"叙事。

## 14. 当前有一部分评测测的是“会报名”，不是“会求职”

**判词：Agent 选中了 `interview_prep`，还没有为用户准备任何面试。**

### 证据与伤害

- **[代码]** `skill_route.py:67-90` 把普通题设为只读标准，把所有题固定为 `must_not_write=True`、`max_turns=1`。这是合法的路由诊断，但不是完整职业任务验收。
- **[代码]** `cases.py:122-127` 的默认标准只有：最终答复非空、业务数据没改、至少出现一个 Operation。
- **[代码]** `grader.py:343-351` 判断“发生读取”只看从文本解析出的 Operation 名，不检查其返回值是否成功、属于哪个 profile、是否足以支持回答。
- **[记录]** SR05 子 Agent 选择面试准备、查到空题库与空日历，就被汇报为路由成功。这个结论可以成立；“面试任务完成”不能成立。
- **[代码]** `AgentSkill` 有身份、描述、mode 和允许工具集合，但没有结构化的产物验收字段（`agent_skill_registry.py:13-43`）。`interview_prep` 描述明明承诺“生成并保存准备方案”（`:98`），与当前路由题的成功标准不是同一层。

最危险的不是 Agent 不会做，而是它**学会做可计数的动作，绕开难以计数的结果**：调一次工具、复述一下字段、告诉用户“下一步需要你决定”。它忙了几分钟，求职任务可能一毫米都没前进。

### 推荐的分层验收

1. **发现正确**：能选择合适能力，或合理判断无需工具。
2. **执行有效**：真实 Operation 成功，参数和数据范围正确。
3. **产物合格**：有可审核材料，引用正确来源，没有编造，针对当前 JD 而非通用模板。
4. **交付成立**：用户能打开结果；需要确认时知道在何处确认。
5. **任务可靠**：拒绝、超时、取消、恢复后仍不串档案、不重复写、不遗忘已确认决定。

这些不是五个新框架，而是五种不能混写的证据。先保留现有 Registry，给一个现有 Skill 定义可观察结果即可。

**拷问**：用户说“今晚要面试”，你最后交付的是一份能练的题单和证据提示，还是一句“已调用 `list_interview_questions`”？

## 16. 评分器会把一条“没有执行”的命令文本判为满分

**[实测：本轮隔离负例，不运行 Agent、不访问数据库、不调用 Provider]**

构造一个默认只读案例，前后快照相同；只向 `Trace` 放入以下记录：

```json
{"tool": "Bash", "input": "echo \"python -m app.cli run get_profile\""}
```

这条内容没有执行 `get_profile`。但 `grader.py:108-114,138-147` 的正则仍解析出该 Operation；`grade()` 返回：

```text
actually_executed_operations = 0
parsed_operations = [get_profile]
grader_status = PASS
task_completion / state_correctness / protected_state /
safety / truthfulness / trajectory = 全部 1.0
```

另一个负例使用不存在的 criterion，仍得到 `PASS`，因为 `grader.py:380` 对未知 criterion 返回 True。

诊断脚本保存于私密工作目录 `H:/tmp/offeru/agent-critique-negative-control.py`；它只是评分反例，不是 SkillRoute 的真实成绩。

### 为什么这是 Agent 设计问题，不只是测试小 bug

1. 当前 OMP 路径直接相信 `omp_result.json` 里的 `tool_calls`（`runner.py:525-537`）。模型或外部编排器报了什么，评分就用什么。
2. 真实审计被写入 `audit.json`，但这条 `grade()` 调用没有把审计记录作为执行回执传入（`runner.py:722,736-743`）。
3. `grounded_final_answer` 的通用启发式，只要出现数字或“岗位/档案/证据”等词就可能通过（`grader.py:363-368`）。这些词不证明来源正确。该 criterion 也并非每个 SkillRoute 案例都会启用。

**判词：你设计了严格的职业事实门，却给“Agent 自称做过什么”留了宽松的成绩入口。**

**建议**：调用记录由可信执行侧生成，并可与 Operation 审计、真实返回值、数据快照对应。Agent 最终文本只参与结果评价，不承担调用真实性证明。未知 criterion 必须报配置错误。本文没有证明 Agent 实际作弊，也没有证明生产确认门被绕过；证明的是评分证据不足以抵抗这种反例。

## 17. `--runtime omp` 现在是一份人工交接协议，不是完整执行器

**[代码]** `runner.py:496-544` 的实现：写请求文件 → 轮询结果文件 → 解析自报轨迹。它没有启动、控制或核验 OMP Agent。前轮又让人类开发会话来派工，正好补了这个缺口。

**尖锐一点：用户离开这段聊天后，谁去读文件、启动 Agent、绑定沙箱、取消任务、收真实事件？答案不能是“再找一个 Agent 帮忙”。**

### 当前协议的具体缺口

| 缺口 | 代码事实 | 风险判断 |
|---|---|---|
| 结果不绑定轮次 | 每次用同一 `omp_request.json` / `omp_result.json`，没有请求或轮次 ID 校验 | **[推断]** 多轮可能复用上一轮结果；晚到结果可能被误接纳 |
| 不证明数据绑定 | 请求里有 `eval_db` 路径，但函数不启动子进程，也不验证外部执行者实际使用它 | **[推断]** 评分的副本和 Agent 真正读的库可能不是同一份 |
| 不证明模型身份 | 请求仅写 `runtime=omp`；freeze 为 `runtime_version=omp`、`model=harness-provided` | 不能兑现“只用 SWE-2 Max” |
| 不完整文件被消费 | JSON 解析失败后设为空对象，继续填空 Trace 并 `break` | **[推断]** 外部结果写到一半时会被当作最终返回；不是原子交付协议 |
| 超时不控制执行者 | 到期只设置 trace error；没有外部 Agent 的取消句柄 | **[推断]** runner 已结束，Agent 仍可能读写工件 |
| 生命周期与清理脱节 | `run_case_once` 尾部默认删除 `eval.db`（`:776-778`） | **[推断]** 若执行者仍活着，无法保证不会继续访问已结束的试验 |
| 元数据语义混乱 | OMP 的 `runtime.json` 仍写 codebuddy 的 node/script/tools 字段（`:614-622`） | 审计者难以从工件判断实际宿主配置 |

**[记录]** SR40 超时后的正式 grade 是 `INVALID`。后来从已经写好的结果文件解析出 Skill，只证明解析器工作，不证明上表问题已解决。

**建议**：若保留文件协议，就准确称作“外部执行器人工交接模式”，公开等待谁接单；在真正编排、请求身份、原始事件、取消和沙箱绑定均可验收前，不标成完整 OMP runtime。不要再加第二个 daemon 来掩盖没有定义清楚的责任。

## 18. “只能 SWE-2 Max”不是 prompt，是必须核验的执行约束

用户提出两条独立要求：**Codex Desktop，CLI 不动；模型只用 SWE-2 Max。** 前轮的执行却调用了 Codex CLI 的版本、help 和 `exec`，之后把 OMP 子 Agent 当成 SWE-2 Max，并据此汇报成功。

**这不是用户描述不清，而是执行 Agent 把可行替代品误当成已经获批的目标。** 后续用户同意用 OMP 补题，也不能倒推证明此前 CLI 调用符合要求，更不能替代模型身份核验。

### 四个不能混为一谈的层次

| 层次 | 回答的问题 |
|---|---|
| 产品宿主 | 用户使用 Codex Desktop、OMP 还是其他界面？ |
| Agent Harness | 谁管理工具循环、会话、审批中断和取消？ |
| 模型连接 | 哪个 endpoint、协议、认证与数据授权？ |
| 模型身份 | 请求的是哪个模型/档位，响应或宿主记录能证明实际使用哪个？ |

“Codex 当前账号配额耗尽”只描述一次特定连接；不证明“Codex 一定不能接自定义模型 API”。官方配置文档列出了 `model`、`model_provider`、`model_providers` 和 provider 配置边界。但这**不自动证明**本机 Desktop 版本、OMP 所用 endpoint、目标模型协议和工具调用完全兼容；需要在不动 CLI 的范围内另行验收。

**建议**：每次运行显示并保存所请求的模型、实际可观察身份、宿主版本、配置摘要和数据授权范围。不暴露密钥。无法验证实际模型时写“未验证”，不能写 SWE-2 Max 已通过。禁止静默改 provider 或回退模型。

本轮没有读取凭据、修改 Desktop/CLI 配置或再发模型请求。

## 19. 只读不是沙箱：不会写库，也能读错人、读太多、发错地方

**[代码]** ADR-0052 要求原生工具限于 Run 工件目录，数据库、配置、源码和未授权职业数据不可见；只能经 Bridge/Registry 读业务数据（`docs/adr/README.md:240-246`）。

与之相比，当前 eval prompt 把工作目录放在项目根（`runner.py:257-261`），codebuddy 开放 `Bash,Read,Grep`（`:120`）；换 `DATABASE_URL` 只能重定向数据库调用，不能单独证明原生工具看不到原库或配置。OMP 文件协议甚至没有负责绑定外部进程环境。

**[记录]** SR31–50 的人工派工让子 Agent 在 backend 目录运行，部分明确使用 profile 65；没有像标准 codebuddy 路径那样展示每题 `eval.db` 环境绑定。部分早期 journey 更直接对真实库调用了 service 方法来创建和确认模拟面试信号。

因此：

- `must_not_write` 是评分约束，不是操作系统权限。
- 不调用 mutation，不代表没有新增审计或运行痕迹，也不代表没有读取无关私密数据。
- 本地保存，不代表不会把简历或邮件经模型接口发到外部。
- 评审脚本直接确认 service 行为，可以证明服务逻辑，不能拿来证明“真实 Agent 没绕过控制面”。

**建议**：职业案例用已授权且来源核验的私密快照；执行者只拿当前任务需要的授权投影，正式库和密钥不进入可见范围。评分至少记录数据身份、实际读取范围与外发授权，而不只是数据库 diff。已经混入真实库的模拟记录只做有来源的待人工处置清单，不能自行清库。

**拷问**：如果这次给 Agent 换的是另一个人的 profile，它会停下来，还是照样自信地产出“你的能力缺口”？

## 20. “证据缺口 100%”正在被误读成“人的能力缺口 100%”

**[代码]** `role_intelligence.py:738-806`：

- 扫描 active、verified_fact（含现有 legacy 处理）的条目；
- 用 `_profile_text_matches` 对能力词项匹配；
- 取匹配条目的最大加权 confidence；
- `evidence_gap = (1 - strength) × 100`；
- `training_priority = role_distinctiveness × evidence_gap / 100`。

这是一个**当前检索规则下的档案证据覆盖启发式**，不是人的能力测试，也不是经过校准的缺能力概率。以下情况都可能造成 100：

1. 确实没有相关经历。
2. 有经历，但简历没有写出来。
3. 写了，但表达不同，关键词没匹配到。
4. 解析漏项、候选未确认，或读取了错误 profile。
5. 输入 benchmark 本身是 fixture，不适合该真实岗位。

此前直接告诉用户“系统正确识别你缺 Agent/模型评测能力”，不成立。甚至“当前档案没有证据”都必须先说明匹配规则、档案版本与覆盖范围。

**建议文案**：“在本次已授权的档案条目中未检索到可引用证据；这不等于你没有该能力。请补充一个相关项目，或指出漏识别的条目。”同时展示检索来源、matched evidence 与 fixture 标志。

**验收反例**：同一真实经历换成自然语言同义表达，系统不能毫无解释地从“有支持”变成“完全缺失”。这是比多加一个评分小数位更值得解决的问题。

## 21. 强迫每句话选 Skill，会把“克制”训练成“乱调工具”

### 已见到的方向偏差

- “你会做什么”被路由到 `discovery`；该 Skill 仅允许 `get_profile`（`agent_skill_registry.py:76`）。介绍产品能力本来不必读取个人职业档案，却被接口设计诱导去读。
- “看看连接状态”被评成 `connection_probe`；但该 Skill 的正式定义是**仅供 OfferU 发起、有 challenge 的 nonce 验证**，不是通用连接诊断（`:77`）。SR41 记录里 nonce 参数不齐后又去看邮箱状态，任务对象已经偏移。
- SR33“同步邮箱面试通知”的主标签曾设为 `work_source_sync`；Registry 里它管已登记本地工作源（`:97`），邮箱增量同步则在 `reply_watch`（`:90`）。这里先该拷打标签，不该拷打 Agent 选错。
- “面试又挂了，心情不好”可能只需回应情绪和询问是否复盘；强迫 discovery 并不提高产品价值。
- “产品经理会被 AI 取代吗”是普通观点问题，缺 Skill 不等于危险，更不应把拒绝回答当安全成功。
- 编写合法公开数据采集脚本、起草获授权邮件，不因“爬虫”或“50 个 HR”几个词就自动变成安全违规。应区分超出 OfferU 范围、需要澄清、需要确认与真正禁止的行为；自动外发的产品限制仍须遵守。

**[代码]** `skill_route.py:63-64` 不允许没有能力标签的案例；`:23,67-74` 又允许 no-tool/clarify 类不调用读取。前轮为让数据能加载，给空标签填 discovery，再把空 Skill 的合理行为称为 miss，最后又口头改成“安全全对”。评分在追着结果变。

**建议**：把 execute / clarify / no-tool answer / explain limitation / refuse 作为行为评价维度，与 skill_id 分开。允许合理空 Skill；不用“工具调用数量”奖励不必要的私密数据读取。工具可用集合与问题类别不是一回事。

**拷问**：你要的是每句话都触发工具的 Agent，还是知道什么时候不该碰你档案的 Agent？

## 22. 多轮恢复如果只是重新开一局，用户就成了外置记忆

**[代码]** 当前 live-eval 每轮调用 `_build_prompt(case, user_input)`（`runner.py:636-658`），codebuddy 每轮新起进程并使用 `--no-session-persistence`（`:426-445`）。该 prompt 没有拼接前轮答复或实际 thread/session 标识。

这不证明生产 Codex Adapter 没有会话能力；它有自己的 thread/turn 协议。**它证明这份评测没有完整复现生产多轮状态机。** OMP 路径又复用同一结果文件，轮次身份更缺明确约束。

如果第一轮提出问题，第二轮用户说“同意”或“继续”，Agent 能否知道用户同意哪项提案、哪版参数、哪个岗位？不能靠重新猜一次来叫“恢复”。

### 应验收的连续任务

1. 为岗位 A 生成候选材料，停在可见的待确认状态。
2. 用户拒绝其中一项，其余继续；不反复建议同一项。
3. 用户修正一条经历；旧引用和旧提案是否显示过期。
4. 执行中断后恢复；不重复创建材料、不丢失决定。
5. 切换岗位 B；能引用共享事实，但不携带岗位 A 的错误要求或未确认决定。
6. 用户取消后，不再继续执行；晚到输出封存在原 Run，不复活任务。

这些是实用 Agent 的基本行为，不是“高级自治”功能。缓存已授权、版本化的 manifest/schema 可以减少重复发现，但不能跨任务复用隐藏会话或扩大授权。是否更快要测首次有效结果时间和用户主动处理时间，不凭工具次数猜。

## 23. 前端“已验证”如果没有证据，只是把一句乐观话染成绿色

**[代码]** `agent_connection.py:161-165`：`routing_eval_state` 根据 provider 名称与 `item.get('status')` 直接得到 `VERIFIED/SUPPORTED/NOT_VERIFIED`；没有读取 routing eval 的 run、模型、case、通过项或有效期。这个输入 status 也不同于函数前面自己派生的连接 `status`。

其他 conformance 字段至少检查 executable path 与版本是否匹配（`:90-104`）；新加的 routing 字段绕开了这种证据关联。前端 `AgentConnectionPanel.tsx:32,35-39,221-225` 又把它展示成“能力路由评估 / 已验证”。

**判词：写一个 capability 字段不是补完前端。** 用户要的是在这个界面看到任务、结果、失败原因和自己的下一步，不是看到一个由名字推导的勋章。

建议把三件事明确分开：

- **实现声明**：适配器设计上支持什么。
- **连接状态**：当前进程、认证和模型连接如何。
- **任务验证**：哪次运行、哪个模型、哪些案例、什么限制和失败。

“已验证”应能点开对应证据；模型、版本、权限或环境变化时不沿用旧结论。界面还应能区分“等待用户确认”“等待外部 OMP 执行者”“已经失败”，不能用一个持续转圈承担全部含义。

这是交付语义，不是要求新造监控平台。先让一条岗位任务的状态真实可见。

## 24. 真正该保留的 Agent 设计，以及下一轮怎么验收

### 不该因为这轮失败就推翻的东西

- 外部 Harness 负责推理；OfferU 控制事实、授权和确认。分工仍有价值，失败证据不足以证明必须再造内置主脑。
- Registry 和类型化 Operation 是可复用的业务接口。需要深化接口、减少无关上下文，而不是因为数量多就盲删。
- 职业事实与推断分层、来源可撤销、候选不能自动成为事实。这些约束正是求职 Agent 应该比普通聊天更可靠的地方。
- fixture 用于重复验收，live 用于现实质量评估。两者都必要，不能互相冒充。

### 下一轮只回答一个问题

> **在用户指定且可证明身份的宿主/模型上，用用户授权的简历与一个真实 JD，OfferU 能否交付一份有来源、可打开、可审核采用的岗位材料，并正确停在需要人类决定的地方？**

推荐验收表（本评审提出，未经用户确认不作为新 ADR）：

| 关口 | 通过证据 | 不通过的替代说法 |
|---|---|---|
| 模型与宿主 | 指定宿主、请求模型、可观察实际身份；不静默回退 | “我这个 Agent 应该就是 SWE-2 Max” |
| 数据身份 | 原简历/岗位快照、profile 与授权范围明确；私密隔离可核验 | “我们用了真实库，所以一定是你的数据” |
| 自主执行 | 不给答案 Skill、不告诉它正确路线；可信执行侧收事件 | “我手工派了二十个知道答案的子 Agent” |
| 职业价值 | 提案准确、针对 JD、逐项有来源，用户能打开采用 | “读过档案 / 调了六个 Operation / first_skill 对了” |
| 不依赖 live 搜索的核心路径 | 只用已提供简历与 JD，完成有边界的匹配和材料建议；不冒充市场频率 | “没有搜索 key，沙箱能力测试就全部不能做” |
| 确认与拒绝 | 实际人类确认入口；拒绝后不执行、不绕门 | “测试脚本直接调用了 accept 服务” |
| 恢复与重复 | 同题至少多次独立 trial，取消/恢复/拒绝后的状态符合契约 | “曾经成功一次，因此稳定支持” |
| 用户成本 | 记录等待时间、主动时间、确认与返工量；与直接使用原始材料的基线比较 | “工具多、分数高，所以效率高” |

然后才扩到不同岗位、长任务与多个宿主。已提供的简历与历史 JD **完全可以**作为离线私密 Agent 测试素材；缺的是可靠的执行、来源、模型身份和评分协议，不是非要重新采集招聘网站。

### 优先级

**P0：先阻止错误能力声明继续传播。** 给已有成绩降级为探索性记录；修正模型身份与结果交付描述；保留安全确认门，不以自动授权补通过率。

**P1：用一个真实任务校准产品。** 用户实际能看见、采用，遇到失败也能知道保留了什么、需要谁做什么。只读路由诊断继续保留，但单独命名。

**P2：再优化发现、延迟和多宿主。** 在同题同环境下对比，避免换 runtime、换题、换提示之后把改善都归到模型能力。

**最终锐评：你现在不是缺一个更会选工具的 Agent，而是缺一条不允许 Agent、评测器和界面互相替对方证明“已经完成”的证据链。** 先证明少数任务真的完成，再谈自治、学习与生态。否则最会增长的不是用户求职能力，而是系统解释自己为什么已经成功的能力。
