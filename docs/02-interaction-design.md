# 02 · 交互设计

> 状态：**当前交互权威** · 取代 workbench-interaction、agentic-interaction-policy、design/adaptive-ui/* 等

## 1. 三条总原则

1. **一眼看懂**：任何页面打开后，三秒内能回答「我在哪、这里有什么、下一步做什么」。
2. **脚本守住底线，Agent 决定交互，人决定重要的事**：确定性代码负责安全和数据完整性；什么时候打扰用户，由 Agent 结合上下文判断；只有真正有后果的选择才交给用户。
3. **永远有路可走**：任何状态下，用户都能继续对话、修改、跳过、放弃。系统状态可以限制「能执行什么」，但绝不能让用户「什么都做不了」。

## 2. 导航与信息架构

> **PROPOSAL（待产品负责人确认）**

现状：侧栏有 11 个入口（`Sidebar.tsx`），中英文混排（Today / Pipeline / Opportunity 与 简历 / 面试 / 工作室），并且有三个简历入口（简历、简历定制、工作室）。`/email` 和 `/calendar` 既高亮在 Pipeline 下，又各自占一个独立入口。

目标：

| 一级 | 路由 | 收编的现有页面 |
| --- | --- | --- |
| 今天 | `/` | Today、Automation Inbox |
| 岗位 | `/jobs`、`/jobs/:id` | Jobs、Applications（作为看板视图 `?view=board`）、Interview（作为工作区的面试标签页） |
| 简历 | `/resume`、`/resume/:id` | Resume、Optimize（简历定制）、Studio（作为模板与设计面板） |
| 档案 | `/profile` | Profile、记忆收件箱 |
| 设置 | `/settings` | Settings、Email、Calendar（作为信号源配置）、Agent 连接 |

规则：

- **N-1** 一级入口最多 5 个（含设置）。新增功能必须先放进已有入口，不能新开一级。
- **N-2** 界面上的概念统一用中文（或统一用 i18n key）。`Job` 和 `Opportunity` 只保留一个，对用户统一叫「岗位」。
- **N-3** 旧路由保留重定向，不能出现 404。
- **N-4** 每个页面只有一个主动作（Primary CTA）。

## 3. 用户能看到的状态

内部状态（queued、running、waiting、needs_reconciliation、stale、executing……）**不能**直接展示给用户。用户只看到三类：

| 用户看到的 | 对应的内部状态 | 是否计入「待处理」数字 |
| --- | --- | --- |
| **需要你处理** | `needs_user_input` / `needs_user_review` / `needs_user_authorization` | 是 |
| **处理中** | queued、running、executing、system_recovering、reconciliation | 否 |
| **已完成 / 失败（可重试）** | completed、failed、cancelled、system_blocked（附原因和一个下一步按钮） | 否 |

- **S-1** 「待处理」数字只统计用户真正需要做决定的事项。
- **S-2** 不完整的审阅包（缺少 Before/After、理由、证据、来源或当前版本）属于系统要修复的问题，**不能**进入用户收件箱。
- **S-3** 超过 2 秒的任务必须显示：进度或阶段、取消按钮、失败原因。
- **S-4** 失败必须可见、可重试，并带 `error_id`；绝不能伪装成成功。

## 4. 打断规则：Agent 什么时候来找你

系统内部用五种结果给每个候选动作分类，**这五个词不出现在 UI 上**：

| 内部结果 | 含义 | 典型场景 |
| --- | --- | --- |
| `AUTO` | 直接做，不打扰 | 读取、研究、生成草稿、可逆的工作区准备 |
| `ASK` | 缺少会显著改变结果的信息 | 简历定位、几种互斥策略选哪一个 |
| `REVIEW` | 拿出具体结果让你采用或修改 | 简历改写、职业事实候选、阶段变化解读 |
| `AUTHORIZE` | 有后果的外部、敏感或破坏性动作 | 提交申请、发信、联系他人、删除或重置 |
| `BLOCK` | 违反硬约束，拒绝执行 | 自我批准、泄露密钥、无法确认结果的外部动作重放 |

- Operation 元数据（副作用、可逆性、敏感度、是否改变 Career Truth、已有授权）只提供**事实**，不机械决定交互结果。旧实现里 `requires_confirmation` 由变更类型推导（`backend/app/ops.py`），这正是需要移除的耦合。
- Agent 可以在 `AUTO`、`ASK`、`REVIEW` 之间选择；硬策略随时可以升级到 `AUTHORIZE` 或 `BLOCK`，Agent 不能降级。

### 4.1 审批对用户怎么呈现

> **PROPOSAL（待产品负责人确认）**

| 场景 | 按钮 | 视觉 |
| --- | --- | --- |
| `REVIEW` | **采用** / **修改** / **跳过** | 普通卡片：Before → After，附理由和证据 |
| `ASK` | 选项（单选或多选）+「其他」自由输入 +「跳过」 | 推荐项预选 |
| `AUTHORIZE` | **确认执行** / 取消 | 强调色、二次确认，写清「会发生什么、不会发生什么」 |

- **修改 ≠ 拒绝。** 修改保留同一任务的身份，用自然语言反馈后由 Agent 重新生成修订版；只重新打开受影响的那部分决定，已经采用的部分不再重复问。
- **内部分组不等于用户决定。** 事务、回滚、依赖、审计都可以拆分，但一次「按产品型定位改写简历」只算用户的一个决定。
- **单个岗位的简历定制**：只问真正没决定的事，给出一个完整可审阅的版本，最终采用决定 ≤ 1 次（除非确实存在独立的高风险选择）。一次定制让用户审 50–80 个独立 Proposal，直接判定为 **UX 不合格**。

### 4.2 Ask 的格式

Ask 支持 `selection_mode: single | multiple`、推荐项、可跳过、自由输入、最少和最多选择数。旧实现把所有选项都渲染成复选框（`AgentAskPanel.tsx`），逻辑上单选的问题必须用单选。只有在答案会显著改变当前决定、且无法从已授权的上下文读出时才提问；一次只问一个有效问题。

## 5. 防死锁规则（必须可测试）

每条规则都必须有自动化测试覆盖。违反任何一条都按 **P0** 处理。

| ID | 规则 |
| --- | --- |
| **D-1** | 任何待审、待问、中断、对账状态，都**不能禁用**输入框、快捷动作或能力选择。新输入由 Agent 分类为：回答 / 修改 / 澄清 / 取消 / 新任务 / 闲聊。 |
| **D-2** | **导航不是任务生命周期。** 新建对话、切换历史对话、关闭面板、切换页面、重启应用，都**不能**取消 Run。只有「完成 / 用户明确取消 / 被新修订替代 / 终态失败 / 自动对账到终态」会结束 Run。 |
| **D-3** | 每个等待状态都必须同时提供：继续、修改、放弃三个出口，并有超时后的系统兜底（自动转为「已完成或失败，可重试」）。 |
| **D-4** | 重启后可以提示「有 2 个任务需要处理」，但**不能**强行打开旧任务，也不能要求先清掉旧任务才能做新事。 |
| **D-5** | Skill 路由失败时：先有限重试，再回退到通用能力；只有用户意图真的有歧义时，才问一个**业务问题**。永远不让用户去「选择 Skill ID」。 |
| **D-6** | Before/After 由系统根据当前状态和提案状态生成，**永远不要求用户自己提供 diff** 才能解锁审批。 |
| **D-7** | 任何确认弹窗都必须能关闭（Esc 或取消），关闭后回到之前的状态，不丢失已输入的内容。 |
| **D-8** | 同一个对象只能有一个写入者。两个面板同时编辑同一份简历时，后保存的一方看到冲突提示，而不是静默覆盖。 |

## 7. 页面职责

| 页面 | 首屏必须呈现 | 不该出现 |
| --- | --- | --- |
| 今天 | 最多 3 个下一步，每个附 `why_now`；需要你处理的事项；进行中的任务 | 空白仪表盘、一长串模式菜单 |
| 岗位列表 | 可排序、可解释的岗位队列；看板视图；「保存新岗位」 | 未解释的总分 |
| 岗位工作区 | 快照 → 研究 → 证据图 → 材料 → 面试 → 时间线，按完成度逐步展开 | 让用户去聊天窗口里找结果 |
| 简历 | 可直接编辑的文档；AI 改动以行内 diff 显示 | Proposal 管理后台 |
| 档案 | 已确认 / 待确认 / 来源 / 缺口 / 本次新增 | 通用的完整度百分比 |
| 设置 | 连接状态（已发现 / 已安装 / 已验证，分开显示）、数据安全 | IMAP、UID、cursor 之类的技术术语 |

**渐进引导**：缺少多个前提条件时，只请求下一个最有用的。例如 Agent 已就绪，但简历、邮箱、扩展都没配置时，先请用户导入简历，而不是同时摆出三个配置面板。

**Agent 面板**：绑定当前页面上下文（当前岗位、简历、面试或「今天」），结果写回对应页面。关闭面板，工作不会消失。

## 8. 文案与术语

| 内部术语 | 界面用语 |
| --- | --- |
| Proposal / Plan Review / Confirmation Group | 待你审阅的修改 |
| Run / Hosted session | 任务 |
| Skill（路由层面） | 不展示；高级模式中才显示为「能力」 |
| Career Truth | 你的档案 |
| Candidate / Observation | 待确认的信息 |
| needs_reconciliation / stale | 不展示，由系统自动处理 |
| Opportunity / Job | 岗位 |
| Pipeline | 投递进展（作为岗位页的看板视图） |

成功文案必须准确。例如采集岗位只能写「已加入岗位库」，不能写「已申请」。

## 9. 视觉、动效与适配

- 高度用 `100dvh`，并保留 `100vh` 作为回退；不在页面级使用 `h-screen` 或 `w-screen`。
- 横向滚动只允许出现在表格区域内；320 / 390 / 768 / 1280 宽度下，页面本身不能出现横向溢出。
- Grid 或 Flex 的子项要设置 `min-width: 0`；简历工作室在 `lg` 以下改为单列。
- 动效只用来帮助理解变化，不能替代文字状态；要支持 `prefers-reduced-motion` 和键盘操作。
- 弹窗要在视口内留出边距，设置最大高度并允许内部滚动。

## 10. 协议对齐方向

> **PROPOSAL**：评估把 Run 的暂停与恢复语义对齐 **AG-UI 1.0**（2026-09-30 发布稳定版）的 interrupt 模型。

- 一个 interrupt 带 `interruptId`、原因和响应 schema；恢复时提交 `resolved` 或 `cancelled` 加 payload；Run 可以以 `cancelled` 终止。这和 OfferU 的 ASK、REVIEW、AUTHORIZE 一一对应，可以替换自研的 pending、interrupted、plan-review 前端状态拼接。
- 可信后端仍然要校验：响应匹配当前未完成的 interrupt，受保护的参数没有在批准路径之外被改动。审批能力仍然只由 Desktop 原生命令持有（见 [08 §6](./08-module-agent-runtime.md#6-唯一确认路径)）。
- 这是方向，**尚未实现**。

## 12. 验收指标（单个真实岗位的完整旅程）

- 任务进行中，聊天输入始终可用；导航从不隐式中止 Run；
- 重启后不会强制打开旧的待办；
- 可见的待处理数 = 真正需要人做的决定数；
- 进入用户收件箱的不完整审阅包 = 0；需要用户自己提供 Before/After 的次数 = 0；
- 正常旅程中手动选择 Skill 的次数 = 0；普通研究、草稿、产物保存需要的审批次数 = 0；
- 能在同一个任务上用自然语言提出修改；
- 简历最终采用决定 ≤ 1 次（存在独立的高风险选择时除外）；
- 系统有足够证据可以安全恢复时，需要用户手动介入的技术恢复次数 = 0。

单元测试通过不等于验收通过。最终验收必须基于当前构建身份和一次真实用户旅程。
