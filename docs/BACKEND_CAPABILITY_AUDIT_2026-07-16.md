# OfferU 后端能力审计

> 日期：2026-07-16  
> 状态：能力审计与核心产品边界已确认，可进入实施拆分  
> 范围：当前桌面运行链、Python 后端、未接入的 Rust 迁移分支，以及与目标能力直接相关的前端本地视觉代码  
> 验证方式：静态代码审计、本机 CLI 契约核对、官方资料与当前开源实现核对；按项目规则未执行构建、语法检查或测试

## 1. 当前结论

当前系统具有可继续演进的基础，但还不能完整兑现四项目标。更准确的定位是：

- 岗位化简历、可定制投递表、邮件解析、文字模拟面试和本地视觉反馈已经形成局部闭环；
- 本地 Coding Agent、长时记忆、跨平台岗位研究、实时进度同步和可配置面试评分仍是部分实现或 PoC；
- README、Python 迁移文档、Rust 迁移文档与桌面启动代码对运行时所有权的描述不一致，必须以当前 Tauri 启动代码为准。

## 2. 已确认的产品边界

- **OfferU 主 Agent**拥有目标理解、记忆、权限、审计和业务状态解释权。
- **本地深度执行器**由主 Agent 按需委托 Codex 或 Claude，用于边界明确的深度研究与批量分析；不拥有业务事实源，不能绕过确认修改求职状态。
- 第一阶段是**单人、本地优先**的桌面产品，当前没有 SaaS 需求；不引入 `workspace_id`、租户、组织、登录、计费或多租户权限。未来若提出 SaaS 目标，再以当时需求独立设计，不让未确认的可能性污染本地版。
- Profile 采用**分层写权限**：职业证据确认后写入；求职偏好可审计、可撤销地自动更新；职业假设独立保存并等待验证，禁止作为事实消费。
- 跨平台公司研究采用**用户授权只读研究**：公开来源自动研究；登录态内容仅在使用者主动发起的本机浏览器会话中读取；不托管账号、不绕过平台限制、不执行站外副作用。
- 研究产物采用**公司档案 + 岗位档案**双层结构；证据按研究运行保留来源和时间，摘要允许刷新但不得静默覆盖旧证据。
- 邮箱或短信等消息先成为**外部进展信号**，再由主 Agent 形成**候选进展**；只有用户确认后才追加正式的**投递阶段事件**并推进当前状态。
- 第一阶段采用**邮箱优先 + 短信转发导入**；不开发或宣称桌面端可直接通用读取手机短信，Android 伴侣留待真实需求验证后再决定。
- 邮箱实时维护采用**托盘驻留的本地同步服务**；OfferU 启动后可在托盘继续增量同步和通知，明确退出后停止，不依赖云端全天候同步。
- 投递表**一行代表一次投递尝试**；同一岗位复投必须创建新尝试，各自保存材料、渠道与阶段时间线，并共享公司档案和岗位档案。
- 进度 UI 采用**摘要表 + 可选阶段列 + 行详情时间线**；表格是阶段事件的派生视图，不再用可覆盖单元格充当投递事实源。
- AI 面试默认将**面试内容评价**与**表达行为反馈**分开展示，不合成单一总分，也不从表情、姿态、手势或声音推断人格、诚信、情绪、录用概率或岗位胜任力。
- 自定义评分采用**声明式、版本化面试评分规则**；允许配置维度、权重、证据、阈值、提示词与聚合方式，但第一阶段禁止执行任意代码或越权读取数据。
- 摄像头只保存**表达行为事件与会话汇总**；原始视频、截图和逐帧 landmarks 不上传、不落盘，所有事件记录检测器版本、时间、次数或持续时长与置信度。
- 第一阶段正式报告统计**姿态片段 + 明确手势 + 可观察面部模式**；表情记录次数、持续时间与置信度，但不参与评分，也不推断心理、人格或录用概率；视线与语音行为留待独立校准后扩展。
- AI 面试、AI 简历优化、岗位研究和投递进展统一产生**学习观察**，由 Memory Service 按分层权限反哺**使用者职业模型**；业务模块不得直接互相改写，也不得把模型评价自动晋升为职业事实。
- 学习观察采用**即时记录 + 空闲巩固**：热路径可靠保存并让当前会话可见，空闲任务完成去重、冲突、过期和晋升建议；巩固失败不得丢失原始观察。
- “同步最新工作内容”只读取用户显式登记的**工作源**，默认排除敏感和生成内容，以增量形成学习观察与待确认职业证据；禁止全盘扫描或把未完成工作自动包装成履历成果。
- OfferU 建设**统一控制台**：GUI、机器 CLI、操作员 TUI 和斜杠 Skill 命令都作为同一 Operation Registry 的薄适配器，共享 schema、权限、确认、审计与错误语义；斜杠命令从 Skill Registry 自动生成，不能成为 shell 或隐藏业务入口。

领域定义见根目录 `CONTEXT.md`，已确认决策记录在 `docs/adr/0001` 至 `docs/adr/0024`；其中 `0001` 已被 `0023` 取代。

## 3. 真实运行链

当前桌面端只启动 FastAPI：

- `frontend/src-tauri/src/lib.rs:1-4` 明确声明只启动 Python AgentKernel；
- `frontend/src-tauri/src/lib.rs:30-51` 以 `OFFERU_PORT=8000` 启动 `backend/run_server.py`；
- `frontend/src-tauri/src/lib.rs:72-91` 只接受 health 中 `runtime=python`；
- `backend/run_server.py:6-10` 绑定 `0.0.0.0:8000`；
- `backend-rs` 的 Rust 8000 前门、Python 8001 代理方案没有进入当前桌面启动链。

因此，当前产品能力必须以 `backend/` 为事实源；`backend-rs/` 只能视为迁移分支，不能用于宣称桌面产品已经具备某项能力。

## 4. 能力矩阵

### 4.1 OfferU 主 Agent与本地深度执行器

**状态：部分实现，Codex 路径当前存在确定性启动故障。**

已有能力：

- `backend/app/services/agent_skill_registry.py:51-83` 静态注册了 31 个工作流技能及 tool allowlist；
- `backend/app/services/harness_agent.py:1226-1240` 将待确认动作持久化为 Run；
- `backend/app/services/agent_run_coordinator.py` 支持确认后执行与中断恢复；
- `backend/app/services/batch_job_evaluations.py` 为每个岗位建立隔离输入、有限并发、逐项状态和可恢复批次；
- `backend/app/services/coding_agent_runtime.py:143-190` 可启动本机 Codex 或 Claude CLI。

关键缺口：

- 本地执行器只接入批量岗位评分，不是主 Agent 可委托的通用研究执行层；
- Codex 参数包含已删除的 `--ask-for-approval never`（`coding_agent_runtime.py:88-102`）。本机 `codex-cli 0.144.1` 已实测返回 `unexpected argument '--ask-for-approval'`；
- worker 依靠模型输出文本后再猜测 JSON，没有使用 Codex `--output-schema` 或 Claude `--json-schema` 做结构化约束；
- MCP 默认关闭；开启后 FastAPI 仍绑定 `0.0.0.0`，`/mcp` 未见认证与调用方身份隔离，不适合直接作为局域网可见控制面；
- 31 个技能为硬编码元数据，不是可安装、可版本化、可校验的用户 Skill 包。

结论：架构方向与已确认的“可选深度执行器”一致，但当前还不可靠，也没有覆盖深度公司研究等目标任务。

### 4.2 长时记忆与 Profile 本体优化

**状态：不满足目标。**

已有能力：

- Agent 对话历史可以持久化；
- `harness_agent_memory.json` 保存 `facts/preferences/goals/risks/events`；
- ProfileSection 支持来源、置信度和 Agent provenance；
- `add_profile_evidence` 会做来源事实门、确定性去重，并通过确认动作后写入 Profile；
- Profile Section 可建立 Qdrant 向量索引，用于 JD 相关条目召回。

关键缺口：

- `backend/app/services/harness_memory.py:175-194` 只按关键词把整段用户消息放入列表，属于启发式日志，不是语义记忆提取；
- `backend/app/services/harness_agent.py:1171-1240` 的记忆主要用于阶段判断、告警和返回快照，没有注入技能 LLM 的证据规划或最终回答；
- 没有事实、偏好、目标、职业假设、会话事件之间的独立类型和生命周期；
- 没有 supersede、冲突解决、版本、来源 turn、用户审阅、遗忘、合并或下游派生物失效机制；
- Agent 写入的 Profile evidence 没有同步调用向量索引入口，语义召回与事实源可能分叉；
- Qdrant 默认 `:memory:`，进程重启即丢索引；embedding 失败返回零向量，可能静默制造无意义匹配；
- “拓展使用者可能性”没有独立的职业假设/探索模型，若直接写进 Profile，会把推测污染成用户事实。

已确认的领域拆分：

1. 职业证据：确认后写入，可被简历、匹配和面试直接引用；
2. 求职偏好：允许自动更新，但每次变化必须可见、可审计、可撤销；
3. 职业假设：独立保存，只有验证并确认后才能晋升为目标方向；
4. 会话与行动事件：保留发生过什么，不直接等于使用者事实；
5. Agent 程序性规则：约束系统如何工作，不属于使用者 Profile。

### 4.3 JD 定制、公司研究、面经与参考简历

**状态：JD 定制基本可用；在线研究不满足。**

已有能力：

- `backend/app/routes/optimize.py:963-1035` 依据单个 JD 召回 Profile 条目、改写、事实校验并生成一岗一简历；
- `backend/app/agents/skills/__init__.py` 串联 JD 分析、匹配、改写、去 AI 痕迹与章节排序；
- 生成简历保留 `source_job_ids`、Profile snapshot 和 section source IDs；
- `InterviewExperience` / `InterviewQuestion` 可以保存手动粘贴的面经并提炼题目。

关键缺口：

- `company_research` 明确标记缺少实时联网研究，允许工具中也没有 web/browser/search；
- 现有 scrapers 只抓岗位，不生成团队、业务、文化、风险、时间戳和来源组成的 Research Dossier；
- 小红书官方开放能力主要面向商品、订单、库存、营销等场景，不提供通用笔记搜索接口；
- 牛客公开 API 文档面向企业版招聘、面试和候选人管理，不等于公开面经内容搜索 API；
- 未发现 BOSS、脉脉面向个人求职调研的稳定公开内容 API；
- 面经目前只能手动录入，没有采集任务、来源快照、引用、去重、时效或可信度；
- “模范简历”没有来源授权、版权边界、匿名化和结构化提炼模型。

现实约束：2025 年生效的《网络数据安全管理条例》要求自动化访问和收集评估对服务的影响，不得干扰服务；最高法相关案例也明确区分用户授权、合理范围内的数据转移与绕过技术措施的大规模抓取/出售。推荐优先级应为：官方公司/ATS 数据、公开网页搜索、用户主动授权的只读浏览器研究、用户手动导入；不建立绕登录、验证码或反爬措施的服务端采集器。

### 4.4 邮箱/短信与投递进度表

**状态：表格底座可用；实时自动维护不满足。**

已有能力：

- `ApplicationTable`、`ApplicationRecord` 与 `ApplicationTableRecord` 支持总表、子表和共享记录；
- 表 schema 支持字段类型、显示、宽度、顺序和选项，可近似截图中的 Notion 式表格；
- 状态更新可以追加事件，支持跟进节奏与漏斗分析；
- Gmail OAuth readonly 和 QQ/163/Gmail/Outlook IMAP 已有连接入口；
- `/api/email/sync` 能拉取最近邮件、用 LLM 分类并创建 `InterviewNotification` 与 `CalendarEvent`。

关键缺口：

- 邮件同步由 POST 手动触发，没有 scheduler、IMAP IDLE、Gmail `watch/history.list` 或本地轮询任务；
- Gmail 官方面向已安装客户端仍建议轮询；若采用服务器 push，需要 Cloud Pub/Sub、持久化 historyId、丢通知回补以及至少七天内续订 watch；
- OAuth token 和 IMAP 密码只保存在进程内存，重启即断开；也没有系统钥匙串/加密凭据存储；
- 通知只写 `InterviewNotification` 和日历，不会自动匹配 `ApplicationRecord`、推进申请阶段或形成待确认变更；
- 没有短信连接代码。桌面程序无法直接通用读取手机短信；Android 通常要求成为默认短信处理应用或满足例外；
- 现有表格只有公司、岗位、地点、链接、来源、薪酬、投递状态、跟进日期和备注等通用字段，没有一面/二面/笔试/测评等阶段实体与时间线；
- 所谓“渐进式披露”目前只是字段 visible 与横向表格，不是“摘要行 → 当前阶段 → 完整事件时间线”的领域模型。

截图中建议建模的列不应全部成为固定列。固定摘要应保留公司、岗位、当前状态、下一动作、下一时间；投递渠道、笔试、一面、二面、HR 面、Offer 等应来自阶段事件时间线，并按需展开。

### 4.5 AI 面试、视觉统计与 Skill 评分

**状态：文字面试和实时本地视觉均已存在，但两者的数据闭环与可配置评分不满足。**

已有能力：

- `/api/interviews` 可按公司、岗位、类型和难度生成题目；
- 用户逐题提交文字答案，后端保存回答、即时评估并生成最终报告；
- `/interview/ai` 已把文字模拟面试与本地摄像头组件放在同一页面；
- MediaPipe Pose、Face 与 Gesture 全部在浏览器本地推理，不上传原始视频；
- 姿态具备个人校准、平滑、综合分和实时反馈。

关键缺口：

- 视觉组件没有 `interview_id`，视觉信号、统计和题目时间段没有写入面试会话；
- 现有 gesture `count` 是连续识别防抖计数，不是“一场面试出现几次”的事件计数；
- 没有视觉事件 schema、采样窗口、置信度、持续时长、去抖规则或会话汇总；
- 后端答案评分固定为结构、相关性、具体性、表达四维，最终报告又使用另一组维度；
- JSON 解析失败会返回固定 70 分，这会把模型故障伪装成真实评价；
- SkillRegistry 是硬编码工作流目录，不能加载用户定义评分标准；
- 没有评分 rubric 版本、权重、阈值、证据字段、维度约束或跨评分器校准数据；
- 将表情或姿态直接解释为人格、诚信、岗位胜任力缺少证据，也会触及生物识别与自动化评价的敏感边界。

推荐边界：原始视频始终留在本地，只上传低频、可解释的派生事件；视觉分与回答内容分分开展示，不把微笑、皱眉或坐姿直接折算成录用概率。

已确认的第一阶段交互方式是“轮次式语音面试 + 文字兜底”：主 Agent 逐题提问，使用者逐题录音作答，本地端点检测结束当前回答，再进行转写和评价。默认保存转写、题目时间范围与派生表达行为事件，不保存原始音频；第一阶段不建设可打断的全双工实时语音链路。

## 5. 横切风险

1. **单用户约束实现得过于偶然**：大量逻辑通过读取第一个或默认 Profile 模拟本地拥有者。当前不需要认证或租户隔离，但仍应把“唯一 LocalOwner/Profile”做成显式的本地仓储约束，避免不同模块各自创建默认记录。
2. **Python/Rust 双事实源**：两个后端都在实现 Agent、Skill 和业务写路径，但桌面只启动 Python；继续双线开发会导致文档与运行事实持续漂移。
3. **能力命名过度承诺**：`native` 有时只表示“能给出文本建议”，不等于完成了用户理解的业务结果。
4. **外部副作用控制不统一**：主 Agent 有确认 Run，但传统 REST、旧 MCP 工具和模块路由仍可绕过同一 Operation Registry。
5. **隐私与审计不足**：邮箱正文、简历、摄像头派生特征和可能抓取的第三方内容缺少统一数据保留、删除、来源与授权记录。

## 6. 推荐目标架构（待讨论）

```text
OfferU 主 Agent
  ├─ Memory Service
  │   ├─ 已验证职业证据
  │   ├─ 当前偏好与目标
  │   ├─ 职业假设
  │   └─ 会话/行动事件
  ├─ Research Service
  │   ├─ 官方公司与 ATS
  │   ├─ 公共搜索
  │   ├─ 用户授权浏览器研究
  │   └─ 手动导入/浏览器扩展
  ├─ Application Pipeline
  │   ├─ 投递记录
  │   ├─ 阶段事件时间线
  │   └─ 邮件/SMS 候选事件 → 人工确认 → 状态变更
  ├─ Interview Session
  │   ├─ 题目与回答
  │   ├─ 本地视觉派生事件
  │   └─ 版本化 Scoring Rubric
  └─ Local Deep Executor Queue
      ├─ Codex adapter
      └─ Claude adapter
```

本地深度执行器的第一阶段职责已限定为可审计重任务：公司/岗位深度调研、批量 JD 评估和已登记工作源的变化摘要。每次执行都必须保留输入、工具轨迹、来源、输出、状态和取消/重放信息；结果返回 OfferU 主 Agent，不能直接写职业模型、确认投递阶段、晋升职业证据或决定面试评分。

来源删除采用级联失效：邮箱消息、工作源或研究材料被删除或撤销授权后，其派生学习观察、候选证据、档案结论和下游引用必须立即退出检索、提示词、评分与记忆巩固。系统仅保留不含原始内容的最小审计外壳；若结论还有其他独立有效来源，则只保留那些来源提供的支持。

调研报告采用“来源分级 + 结论逐条引用”的最低证据门槛。公司业务、岗位要求等硬事实优先由官网、招聘官网与正式公告支撑；团队氛围、面经等主观信号至少需要两个彼此独立的近期来源交叉验证。只有单一来源时必须标记为单一信号，没有可靠证据时标记为未知，不允许由模型补全为确定事实。

“模范简历参考”只以匿名简历表达模式进入岗位档案：系统提炼结构、能力表达与量化方式，并保留来源和授权状态；不得建立真实候选人完整简历库，也不得近似复刻个人简历。参考模式只能影响表达建议，最终简历中的经历、技能和成果仍必须由使用者职业证据支撑。

外部进展信号的关联采用“确定性标识优先 + Agent 辅助识别”。申请编号、邮件线程、明确公司域名与岗位标识用于形成确定性候选；Agent 负责从非结构化内容中识别公司、岗位、招聘批次并对可能的投递尝试排序、给出理由。若存在多个合理候选或只有语义相似，必须由使用者选择；无法判断的消息进入待归属队列。Agent 不得直接建立正式关联或写入投递阶段事件。

邮箱连接凭据使用操作系统钥匙串保存：Windows 使用 Credential Manager，并为 macOS Keychain 与 Linux Secret Service 保留适配接口。SQLite 只保存账号元数据、授权范围和不透明的凭据引用；OAuth token、IMAP 应用密码等原始密钥不得进入数据库、配置文件、日志、遥测或 Agent 上下文。

第一阶段以 Python/FastAPI 为唯一业务后端。`backend-rs` 冻结 Agent、Skill 和领域写路径的迁移，不再与 Python 双写业务能力；Tauri/Rust 只负责桌面壳、系统托盘、操作系统钥匙串、进程生命周期和其他必要系统桥接。未来是否迁移某个深模块，必须由可测量的性能、安全或分发收益驱动，并以稳定领域契约为前提。

邮箱正文采用最小证据快照策略。默认只持久化 message-id、线程标识、发送者、时间、主题、与阶段判断相关的片段和正文哈希；完整正文只在同步与解析期间短暂存在，除非使用者对单封消息显式选择保存。快照用于核对 Agent 的关联和阶段判断，但不把 OfferU 变成完整邮箱副本。

本地敏感数据采用统一静态加密：由操作系统钥匙串保护主密钥，数据库、简历附件、使用者显式保存的邮件正文、搜索索引、缓存和备份使用同一安全边界。应用解锁后透明读取，但不得出现“主库已加密、索引或临时副本仍为明文”的旁路。

总职业模型的变更建议通过记忆收件箱审核。每条建议必须展示变更前后差异、生成理由、证据来源、影响范围和建议类型，并支持接受、拒绝、稍后处理与撤销；业务对话可以提示待处理数量，但不以频繁弹窗打断任务，也不允许系统先改写后通知。

敏感求职材料发送至云端模型采用数据分级授权。本地确定性解析和脱敏优先；使用者按具体模型供应商授权简历、邮件片段、面试转写等数据类别，运行前必须展示将发送的数据类别。配置 API Key 仅建立供应商连接，不等于授权发送全部数据；授权可以撤回，撤回后相关任务必须在调用前失败关闭。

第一阶段按四个垂直闭环交付：先修复唯一 Python 运行链并建立观察、来源、事实门、加密与审计底座；再完成邮箱到候选进展、确认和投递时间线；随后完成公司/岗位档案到 JD 分析和证据化简历优化；最后把现有摄像头 PoC 接入轮次式语音、表达行为事件与版本化评分规则。每阶段必须从用户触发贯通到可见结果并可独立验收。

## 7. 决策完成与实施入口

核心架构与产品边界已经全部确认。实施采用三层量化验收：权限、来源、删除、密钥、原始媒体等安全不变量要求 100% 通过；Agent 分类、字段提取、行为检测等概率能力在固定标注样本集上达到明确阈值；每个垂直阶段还必须通过真实端到端用户场景和重启、重试、重复输入故障测试。禁止用“页面能打开”或一次演示成功替代验收。

具体交付顺序、阶段范围和发布门槛见 `docs/IMPLEMENTATION_ROADMAP_2026-07-17.md`。
