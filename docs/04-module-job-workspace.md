# 04 · 模块：岗位工作区

> 状态：**当前设计权威** · 取代 browser-extension、site-rule-pack-v1（用户侧部分）、owner-career-journey §4–5、career-operations-loop §8–10 等
> 用户入口：一级导航「岗位」 · 主要代码：`backend/app/services/job_*`、`role_intelligence.py`、`career_job_assessment.py`、`application_workspace.py`；`frontend/src/app/jobs/`；`extension/`

## 1. 目的

一个岗位不是一张详情页，而是这个机会的**持久工作区**。Agent 的工作结果会逐步沉淀在这里，关掉聊天窗口也不会丢。

```text
岗位工作区
├─ 岗位快照      JD 原文、来源、采集时间、是否仍有效
├─ 研究          Role Intelligence：共性要求 / 独特要求 / 公司与团队
├─ 证据图        岗位要求 × 我的证据：强 / 弱 / 缺失 / 未知 / 表达不足
├─ 材料          本岗位使用的简历版本、求职信、申请问题
├─ 面试          轮次、准备、复盘（见 07）
└─ 时间线        所有事件 + 下一步
```

## 2. 岗位从哪里来

| 来源 | 默认 | 规则 |
| --- | --- | --- |
| **浏览器扩展：采集当前页面** | ✅ 新手默认 | 用户主动点击才读取当前标签页；先预览和去重，再保存 |
| 粘贴链接或 JD 文本 | ✅ | 同样经过预览和去重 |
| Skill-first：在 Agent 里说「分析这个岗位」 | ✅ | 创建或找到**同一个**岗位 |
| 官网、公开招聘源、已授权的平台（如 BOSS） | 高级用户 | 有来源范围、预算、去重、暂停和失败展示；属于研究能力，不是后台爬虫 |

保存岗位 ≠ 已投递。成功文案只能写「已加入岗位库」。

## 3. 浏览器扩展（只做三件事）

1. **采集**：在当前招聘页生成岗位预览，缺失的字段明确标出，不猜测 → 加入本地岗位篮 → 「确认同步 N 个岗位到 OfferU」。逐条成功之前不删除本地条目，重复同步保持幂等。
2. **安全填表**：第一步固定是「扫描表单（不会填写）」。字段分为：可填写 / 受保护（已有值、身份、薪资、工作许可、同意项、附件）/ 需要你处理 / 未识别。二次确认时写清楚：不会覆盖已有值、不会上传附件、不会勾选同意项、不会提交。计划绑定 URL、字段指纹和过期时间，页面一变就要求重新扫描。逐字段返回结果，部分失败不能显示为整体成功。
3. **提交回执**：用户自己提交后，点击「我已自行提交，检查结果」。至少需要两组独立的成功证据，并把校验错误、草稿、登录、验证码作为反证。用户点「确认已提交并记入」后，才原子地创建一个 `ApplicationAttempt` 和一个 `Submitted` 事件。

扩展**永远不执行最终提交**。站点适配用 `SiteRulePack`（纯数据，不含 JS 或提交按钮选择器）和随扩展打包的 `ControlDriver`；只有 `verified` 规则可以启用写能力。规则的精确 schema 以 `extension/src/rule-packs/contracts.ts` 为准。

## 4. 岗位排序

评分用来帮助排序，**不是**录取概率预测。

- 维度、权重和证据都可以展开查看：硬条件、职责 / 能力匹配、可验证的经历、目标独特点、个人偏好、已知风险、信息新鲜度、不确定性。
- 信息不足时要解释影响，不能给固定的假分，也不能把未知当作 0 分。
- 用户修改目标后，排序要能解释为什么变了。
- 用户按条或按组选择「今天推进 / 暂缓 / 不考虑」。「推进」只启动研究和材料准备。
- 已拒绝、已过期或长期被忽略的建议要降权，不能每天重复出现。
- 每日推荐必须真的拿到了新数据；如果只是对旧库重新排序，要标明「基于旧数据」。

## 5. 保存岗位之后发生什么

```text
JOB_SAVED
  → Career Director 做一次有边界的评估（读取当前职业状态）
  → 计划写入 CareerTask / 收件箱，显示在工作区
  → 如果建议做 Role Intelligence → 用户一键开始（L1，在范围内自动执行）
```

- 没有可用 Agent 或模型时：岗位照常保存，工作区照常可用，记录一个可重试的 blocked CareerTask，并说明需要配置什么。**不能**用脚本伪造一份评估。
- Role Intelligence **不会**因为 `JOB_SAVED` 自动启动。

## 6. Role Intelligence

以目标 JD 为中心，对比可比的公司、岗位族和 seniority，不把相邻但不同的岗位混进来。

| 结果 | 依据 | 用途 |
| --- | --- | --- |
| 同类岗位共性能力 | 可比样本中实际出现的要求及出现次数 | 简历的基础表达、面试基本功 |
| 目标岗位独特点 | 目标 JD 明确写出、与样本不同的要求 | 有证据支撑的重点经历、专项练习 |
| 本人证据与缺口 | 原简历、已确认的档案、项目来源 | 能突出的、需要补证据的、暂时不能声称的 |

- Runtime 负责样本集、去重、统计和差异（Delta）；Agent 负责收集和解释。**不能**由模型编造市场比例。
- 保留每个对照 JD 的来源和时间；样本不足、页面打不开、岗位身份不明，都展示为缺口。
- 公司和团队研究也存在同一个工作区里，分别标注：公开来源 / 本人沟通记录 / 社区单一信号 / 推断。
- 牛客、小红书、公开简历只作为带时间和来源的参考信号；不复制他人的身份、成绩或完整简历。
- **同一份 Role Intelligence 同时驱动简历和面试**（资产 ID、版本、来源一致），不能在两次聊天里分别重做一遍研究。

## 7. Fit Check 与投递协助

- Fit Check 逐条列出要求对应的证据、硬性要求和未知项；没有解释的总分不能作为决策依据。
- 投递流程：OfferU 准备 → 用户审阅 → 确认后填写安全字段 → **用户自己完成最终提交** → OfferU 生成回执候选。
- 申请材料、问题、审批和回执都汇集在同一个工作区里。**不新建**平行的 Opportunity、Application Packet 实体或生命周期。
- 自动注册账号、重复联系招聘方等属于单独的外部动作需求，当前**不支持**。没有合法执行路径时就展示缺口，不能绕过 Registry 在浏览器里悄悄执行。

## 8. 状态

| 状态 | 用户看到的 |
| --- | --- |
| 快照就绪 | 「岗位已保存」 |
| 评估中 / 评估被阻塞 | 「正在评估」 / 「需要连接 Agent 才能评估」+ 按钮 |
| 研究就绪 | 研究卡片展开 |
| 有待审阅的修改 | 计入「需要你处理」 |
| 已投递（有回执证据） | 时间线新增「已提交」 |
