# Dogfood 记录

用户用 OfferU 真实求职，同时在优化 OfferU 的 agent。每次帮他做事，都是一次真实试用：不顺的地方是待修的工具问题，用户的反馈是人工偏好信号（RLVR 里的人工标注）。文件是 docs/DOGFOOD.md。

## 什么时候记

当轮就记，不要留到最后，也不用先问用户。

- 工具卡点：OfferU 工具（add_job、evaluate_jobs、tailor_resume 等）报错、缺参数、结果不对、太慢（超过 60s 或被转后台）；网页抓不到、要人工转写；开发环境或 agent harness 让你多跑了一轮。
- 用户偏好：用户说“要加 X”“不要这样”“以后都…”，或纠正了你的产出（文案、评分、取舍、顺序）。
- 产出里提出了要问用户的取舍：先记成“待确认”，用户答了再改成偏好。

## 怎么记

1. 先读 docs/DOGFOOD.md，同一个问题已经有行就更新那一行，不重复加。
2. 工具卡点表加一行：日期 | 工具 / 环节 | 现象 | 影响（多几轮、等多久、用户看到什么）| 待办（具体到改哪个工具或参数）。
3. 用户偏好表加一行：日期 | 场景 | 偏好（尽量用用户原话，不放大成“总是”）| 落到哪（提示词、字段、工具）。
4. 修好了在行尾标「→ 已修 <commit>」，不删行。
5. 写完在回复里一句话告诉用户记了什么；DOGFOOD.md 跟当轮的代码改动一起提交。

## 规则

- 只写事实，不写推测的原因；不确定就写“待查”。
- 不写用户隐私：手机、邮箱、身份证、密码、token、完整 JD 或简历原文。岗位用 #id 指代。
- 真实数据要先脱敏，才能进回归测试集。
- 改提示词、工具或评测之前先读本文件，先做影响大、重复出现的卡点；做法和已记录的偏好冲突时先问用户。
- 这是开发侧的 skill，不打包进 offeru connect 给用户装的 offeru skill。
